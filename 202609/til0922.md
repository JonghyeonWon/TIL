## 1. Spring Data Core와 Spring Data JPA

- `Pageable`, `Page`, `Sort` 등은 JPA 전용 기능이 아니라 `spring-data-commons`(Spring Data Core)에 정의된 공통 기능이며, `spring-data-jpa`는 그 위에 JPA 전용 기능(`JpaRepository`, `@Query` 등)을 더한 것

- 구조:

    ```
    spring-data-commons (Core)
      Repository, CrudRepository, PagingAndSortingRepository
      Page, Pageable, PageRequest, Slice, Sort
              ▲
      ┌───────┼────────┬──────────┐
    spring-data-jpa  -mongodb  -redis  -jdbc
    ```

- 여러 저장소 모듈이 같은 계약(`Pageable`/`Page` 사용법)을 재사용하기 위해 나눈 것이므로, MongoDB로 바꾸더라도 `Pageable`을 넘기고 `Page`를 돌려받는 방식은 동일함
- 다만 상속할 인터페이스, `@Query` 문법(JPQL ↔ JSON), 엔티티 매핑(`@Entity` ↔ `@Document`)은 저장소마다 달라짐

## 2. 페이징(Paging)  

- 페이징의 본질은 데이터베이스가 전체 결과 중 일부만 잘라서 반환하는 것(`LIMIT` / `OFFSET`)이며, `Pageable`은 결국 이 SQL을 만들기 위한 값

- DB마다 페이징 SQL 문법이 다름 → JPA는 `Dialect`가 이 차이를 대신 처리하므로 `Pageable`만 넘기면 DB를 교체해도 코드를 고칠 필요가 없음

- `ORDER BY`가 없으면 순서가 보장되지 않아 페이지마다 결과가 달라질 수 있으므로 페이징 SQL에는 정렬이 필수

### Pageable 만들기

```java
Pageable pageable = PageRequest.of(0, 10);                              // 0번 페이지, 10건
Pageable pageable = PageRequest.of(0, 10, Sort.by("name").ascending()); // 이름 오름차순
Pageable pageable = PageRequest.of(1, 5, Sort.by(Sort.Direction.DESC, "id"));
```

- `page`는 **0부터** 시작  
- `Pageable`은 `pageNumber`, `pageSize`, `sort` 세 가지만 클라이언트가 지정하고 `offset`은 `pageNumber * pageSize`로 계산됨  

    | 속성 | 의미 | 결정 |
    | :--- | :--- | :--- |
    | `pageNumber` | 몇 번째 페이지인가 (0부터) | 클라이언트 지정 |
    | `pageSize` | 한 페이지에 몇 건인가 | 클라이언트 지정 |
    | `sort` | 정렬 순서 | 클라이언트 지정 |
    | `offset` | 앞에서 몇 건 건너뛸지 | 계산됨 (`page * size`) |

## 3. `Page<T>`  

```json
{
  "content": [ ... ],
  "pageable": { "pageNumber": 1, "pageSize": 3, "offset": 3, "sort": {...} },
  "totalElements": 8,
  "totalPages": 3,
  "number": 1,
  "size": 3,
  "numberOfElements": 3,
  "first": false,
  "last": false,
  "empty": false
}
```

- `size`(요청 크기)와 `numberOfElements`(실제 담긴 건수)는 다름 → 마지막 페이지에서는 `numberOfElements`가 더 작을 수 있음

- `totalElements`, `totalPages`는 별도의 **count 쿼리**를 실행해야 알 수 있는 값

- `first` / `last`로 화면의 이전/다음 버튼 활성화 여부를 판단

### Page / Slice / List 차이

- `Page`: 전체 건수를 알려주는 대신 count 쿼리를 한 번 더 실행
- `Slice`: `size + 1`건을 조회해서 다음 페이지 존재 여부만 판단 → count 쿼리가 없어 더 빠름
- 전체 페이지 수를 화면에 표시하지 않는다면 `Slice`가 유리

## 4. Pageable / DTO  

- 메서드 파라미터에 `Pageable`을 선언하면 스프링이 요청 파라미터(`page`, `size`, `sort`)를 자동 변환  

- `@PageableDefault`로 파라미터 생략 시 기본값 지정 (생략하면 기본값인 `size=20` 적용)  

- 기본 최대 크기는 2000이며 `spring.data.web.pageable.max-page-size`로 조정 (클라이언트가 큰 값을 보내도 이 값으로 제한)  

- 엔티티를 그대로 반환하지 않으므로 `Page<Student>.map()`으로 페이지 정보는 유지한 채 내용만 DTO로 변환

    ```java
    public Page<StudentDTO.Response> getAllStudents(Pageable pageable) {
        Page<Student> students = studentRepository.findAllWithDetails(pageable);
        return students.map(StudentDTO.Response::fromEntity);
    }
    ```

- 정렬을 지정하지 않으면 순서가 흔들려 같은 행이 여러 페이지에 중복되거나 빠질 수 있으므로 `@PageableDefault(sort = "id")`처럼 기본 정렬을 두는 것이 안전

## 5. 페이징과 Fetch Join — N+1 문제

- `LEFT`/`INNER`는 **어떤 행을 남길지**를 정하고, `FETCH`는 **조인한 엔티티를 함께 로딩할지**를 정함 (서로 다른 축의 개념) → `LEFT JOIN FETCH`처럼 겹쳐 사용  

- `FETCH`가 없으면 조인은 조건/집계용으로만 쓰이고 연관 엔티티는 가져오지 않아, 나중에 접근할 때 추가 쿼리(N+1 문제)가 발생  

### 핵심 규칙: 1:N 컬렉션 Fetch Join + 페이징을 함께 쓰지 않기  

- 컬렉션을 Fetch Join하면 부모 1건이 자식 수만큼 행으로 늘어나므로, DB의 `limit`으로는 원하는 개수만큼 부모를 정확히 자를 수 없음
- Hibernate는 이 경우 SQL에서 `limit`을 빼고 전체를 읽은 뒤 **메모리에서** 페이징하며 경고를 남김:

    ```
    WARN HHH90003004: firstResult/maxResults specified with collection fetch;
                      applying in memory
    ```

- 데이터가 많아지면 느려지고 `OutOfMemoryError`로 이어질 수 있는데, 예외가 아닌 경고만 나와 놓치기 쉬움

### 네 가지 조합 비교

| 조합 | 결과 |
| :--- | :--- |
| 컬렉션 `FETCH JOIN` + 페이징 | 경고 발생, `limit` 없이 전체를 읽어 메모리에서 자름 |
| `FETCH` 제거(일반 조인) + 페이징 | `limit`은 붙지만 조인으로 행이 늘어나 결과/`totalElements`가 틀어짐 |
| 프로젝션(`d.id`, `COUNT(s)`)에 `FETCH` 사용 | `SemanticException` — 연관관계 주인이 SELECT 절에 없어 앱 기동 자체가 실패 |
| 일반 `JOIN` + `GROUP BY` 프로젝션 | 정상 — 학과당 1행이 되어 `limit`이 정확히 동작 |

- 해결책:
  1. 목록 화면처럼 자식 개수만 필요하면 **프로젝션으로 집계**(`COUNT(s)`)해서 컬렉션 로딩 자체를 회피  

  2. 자식 목록까지 필요하면 부모만 페이징하고 `spring.jpa.properties.hibernate.default_batch_fetch_size`로 자식을 `IN` 절 묶음 조회로 채움  

  3. 개발 중에는 `hibernate.query.fail_on_pagination_over_collection_fetch=true`로 경고를 예외로 승격시켜 실수를 조기에 발견

### countQuery 관련 규칙

- `countQuery`는 **전체 건수를 세는 쿼리만** 바꿀 뿐, 목록 쿼리의 메모리 페이징 문제와는 무관  

- `countQuery`를 생략하면 Spring Data가 원본 쿼리에서 `FETCH`를 떼어내 count 쿼리를 자동 생성하는데, 연관 엔티티 경로를 조건(`WHERE s.department.id = :id`)에 쓰면 조인이 남아 불필요한 조인이 발생할 수 있음 

- 직접 쓴 `countQuery`의 `WHERE` 조건은 목록 쿼리와 반드시 동일하게 맞춰야 `totalElements`가 정확함
