## 1. Entity 연관관계(One to One)  

- 객체는 양쪽에서 서로를 참조할 수 있지만, DB의 외래키(FK)는 한 곳에만 존재하므로 외래키를 관리하는 주체가 연관관계의 주인이 됨  

- `@OneToOne`, `@ManyToOne`, `@OneToMany`, `@ManyToMany`중 하나를 두 객체에 명시  

- 주인: `@JoinColumn`을 사용하며 주인임을 명시  
- 비주인: `mappedBy` 속성을 사용  

- 비주인 쪽에만 값을 설정할 경우 DB에 FK의 값이 저장되지 않음  

- `CascadeType.ALL`: 대상의 상태를 변화시킬 때 연관된 객체들에 대해 동일하게 변화를 전달

## 2. 지연 로딩(LAZY) / 즉시 로딩(EAGER)  

- `JPA`의 `FetchType`은 연관 관계에 있는 엔티티를 언제 DB에서 로드할지를 결정하는 전략  

-`FetchType.LAZY`

    - 연관된 엔티티를 실제로 `getter` 메서드로 호출할 때까지 로딩을 지연  
    - 프록시 객체를 생성하여 실제 데이터가 필요한 순간 쿼리 실행  
    - 메모리 효율적이고 초기 로딩 시간이 빠름  
    - 연관 데이터를 쓸 때마다 추가 쿼리가 발생하는 `N+1 문제` 발생  

-`FetchType.EAGER`

    - 엔티티를 로딩할 때 연관된 엔티티를 즉시 함께 로딩  
    - 메모리가 많이 필요하고 조회 시간이 오래 걸림  
    - 연관관계가 커질수록 어떤 쿼리가 나갈지 예측하기 어려움  

- 모든 연관관계를 `LAZY`로 설정하는 것이 원칙  

    - `@OneToOne` : 기본값이 `EAGER` → `FetchType.LAZY` 를 직접 지정  
    - `@ManyToOne` : 기본값이 `EAGER` → `FetchType.LAZY` 를 직접 지정  
    - `@OneToMany` : 기본값이 `LAZY`
    - `@ManyToMany` : 기본값이 `LAZY`  
    
    - 연관 데이터를 함께 조회해야 할 때는 EAGER로 바꾸는 것이 아니라 `Fetch Join`을 사용

## 3. Fetch Join / N+1 문제  

### 3.1. N+1 문제  

- 1번의 쿼리로 N개의 목록을 조회했을 때, 연관 데이터를 가져오기 위해 N번의 추가 쿼리가 실행되는 문제 (총 1 + N번 실행)  
- `LAZY` 로딩 상태에서 N개의 엔티티를 조회한 후, 루프를 돌며 연관 객체의 `getter`를 호출할 때 발생  

### 3.2. Fetch Join  

- JPQL 전용 기능으로, `LAZY`로 설정된 연관 엔티티를 한 번의 SQL 쿼리로 가져오는 기능
- 엔티티의 `FetchType` 설정을 `EAGER`로 바꾸지 않고, 필요한 시점에만 선택적으로 한 번에 가져올 수 있음  
- N+1 문제를 해결하는 가장 기본적인 방법  

### 3.3. 일반 JOIN vs FETCH JOIN  

- **일반 JOIN**:

  - 연관 엔티티는 여전히 프록시 상태로 남으므로 나중에 추가로 사용 시 추가 쿼리 다시 발생

- **FETCH JOIN(JOIN FETCH)**:

  - 메인 엔티티와 연관 엔티티를 모두 SELECT하여 실제 데이터 객체로 채움
  - 추가 쿼리가 발생하지 않아 N+1 문제 해결 가능  

### 3.4. INNER JOIN FETCH vs LEFT JOIN FETCH  

- **`JOIN FETCH`(내부 조인)**:

  - 두 테이블 모두에 값이 존재하는 행만 조회됨
  - 연관 데이터(예: 학생의 상세정보)가 없는 엔티티는 조회 결과에서 누락되는 문제 발생

- **`LEFT JOIN FETCH`(외부 조인)**: 

  - 연관 데이터가 없어도 주 엔티티를 정상 조회함 (연관 객체는 `null` 할당)
