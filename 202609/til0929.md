## 1. 공통 응답과 예외 처리 (common)  

### 1-1. 응답 봉투

- 성공과 실패 모두 같은 모양의 JSON으로 감싸서 프론트가 `success` 하나로 분기할 수 있게 함  

    ```java
    public record ApiResponse<T>(boolean success, T data, String message, OffsetDateTime timestamp) { }

    public record ErrorResponse(boolean success, int statusCode, String code, String message,
                                List<FieldError> fields, OffsetDateTime timestamp) { }
    ```

- `ErrorCode` enum 하나에 **HTTP 상태 + 기본 메시지**를 같이 묶어 둠 → 서비스는 `throw new BusinessException(ErrorCode.PRODUCT_NOT_FOUND)`만 하면 상태 코드는 핸들러가 알아서 결정  

    ```java
    PRODUCT_NOT_FOUND(HttpStatus.NOT_FOUND, "상품을 찾을 수 없습니다"),
    PRODUCT_NOT_ON_SALE(HttpStatus.CONFLICT, "판매 중인 상품이 아닙니다"),
    ```

### 1-2. `@ExceptionHandler` 선택 기준  

- `GlobalExceptionHandler`에 핸들러가 여러 개 있을 때, **파일에 적힌 순서가 아니라** 발생한 예외 타입과 **상속 관계상 가장 구체적인** 핸들러가 선택됨  

- 그래서 `Exception.class` 핸들러가 위에 있어도 `BusinessException`은 `handleBusiness`로 감 → `Exception` 핸들러는 나머지를 받는 **최후의 안전망(500)** 역할  

### 1-3. JSON 변환 → `@Valid` 순서  

- 요청 처리 순서: **JSON → 객체 변환(Jackson이 수행)** 이 먼저, 그 다음 과정이 **`@Valid` 검증**  

    | 실패 시점 | 예외 | `fields` |
    | :--- | :--- | :--- |
    | JSON 변환 실패 (타입 불일치, 깨진 JSON) | `HttpMessageNotReadableException` | `null` |
    | Bean Validation 실패 (`@NotBlank`, `@Pattern` 등) | `MethodArgumentNotValidException` | 필드별 메시지 채워짐 |
    | 서비스에서 직접 던짐 | `BusinessException(VALIDATION_ERROR)` | `null` |

- 변환에 실패하면 객체 자체가 만들어지지 않으므로 검증은 **실행조차 되지 않음** → 어느 필드가 틀렸는지 알려줄 수 없음 → `fields` 값이 `null`

- `categoryId`를 `Long`이 아니라 `String` + `@Pattern`으로 받은 이유  

    ```java
    @NotBlank(message = "카테고리는 필수입니다")
    @Pattern(regexp = "\\d{1,18}", message = "카테고리 값이 올바르지 않습니다")
    String categoryId
    ```

    - `Long`이면 `"abc"`가 들어왔을 때 변환 단계에서 실패해서 `fields` 값이 `null`인 400이 됨  
    - `String`으로 받으면 변환은 항상 성공하고, 검증 단계에서 걸러지므로 `fields`가 있는 **`categoryId` 필드 에러**로 응답 가능  

### 1-4. `/admin` 예외 처리  

- 관리자 화면은 JSON API가 아니라 **서버 렌더링 화면**이므로 공통 JSON 봉투로 응답하지 않음 

- `GlobalExceptionHandler`는 요청 URI가 `/admin`으로 시작하면 예외를 다시 던져(`throw e`) JSON 처리에서 빠짐  

- 관리자 컨트롤러에서 난 예외는 `AdminControllerExceptionHandler`가 받아서 **flash 메시지 + 이전 페이지(Referer)로 redirect됨** 

    ```java
    redirectAttributes.addFlashAttribute("adminError", "일시적인 오류가 발생했습니다. ...");
    String referer = request.getHeader("Referer");
    return "redirect:" + (referer != null ? referer : "/admin");
    ```

## 2. 엔티티 설계   

### 2-1. `@NoArgsConstructor`에서 `protected` 기본 생성자가 필요한 이유

- JPA(Hibernate)는 DB에서 조회한 값을 채우기 위해 **리플렉션으로 기본 생성자를 호출**하고, 지연 로딩용 **프록시**도 엔티티를 상속해서 만들기 때문에 기본 생성자가 필요  

- `public`으로 열면 아무 데서나 빈 엔티티를 만들 수 있으므로 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`로 JPA에게만 열어 둠  

### 2-2. 빌더로 초기 상태 고정  

- `@Builder` 생성자에서 상태를 **`INSPECTING`으로 고정** → 등록하는 쪽이 상태를 마음대로 정할 수 없음  

    ```java
    @Builder
    public Product(User seller, Category category, String title, ...) {
        ...
        this.status = ProductStatus.INSPECTING;
    }
    ```

### 2-3. `@MappedSuperclass`와 Auditing  

- `BaseEntity`에 `createdAt`을 두고 엔티티들이 상속 → 테이블은 따로 생기지 않고 **컬럼만 물려받음**  

- `Auditing` 동작 조건 (셋 중 하나라도 빠지면 값이 안 채워짐)  

    1. `@EnableJpaAuditing` (설정 클래스)  
    2. `@EntityListeners(AuditingEntityListener.class)` (`BaseEntity`)  
    3. `@CreatedDate` / `@LastModifiedDate` (필드)  

- 시드 SQL(`data.sql`)의 `NOW()`는 JPA를 거치지 않고 DB에 직접 넣는 값이므로 **Auditing과 무관**  

### 2-4. 연관관계 주인과 cascade / orphanRemoval  

- 외래키(`product_id`)를 가진 `ProductImage`가 **연관관계의 주인**, `Product.images`는 `mappedBy = "product"`로 읽기 전용  

- 양쪽을 한 번에 맞추기 위해 편의 메서드 사용  

    ```java
    public void addImage(ProductImage image) {
        images.add(image);       // 객체 쪽 컬렉션(product에 image 추가)
        image.assignTo(this);    // 실제 FK를 결정하는 주인 쪽(productImage에 product 추가)
    }
    ```

    | 옵션 | 의미 |
    | :--- | :--- |
    | `cascade = ALL` | 부모를 저장/삭제하면 자식도 **같이** 저장/삭제 |
    | `orphanRemoval = true` | 부모 컬렉션에서 **빠진** 자식을 DB에서도 삭제 |

### 2-5. 지연 로딩(LAZY)과 프록시  

- `@ManyToOne(fetch = LAZY)`면 연관 엔티티 자리에 **프록시**가 들어가 있고, 실제 필드에 접근하는 순간 쿼리가 나감  

- 단, `getId()`는 프록시가 이미 id를 알고 있으므로 **쿼리가 나가지 않음**  

- `open-in-view: false`이므로 트랜잭션(서비스)이 끝난 뒤 서비스 밖인 컨트롤러에서 프록시를 건드리면 `LazyInitializationException` → **DTO 변환은 서비스 안에서** 끝내야 함  

- EAGER 대신 LAZY를 쓰는 이유: EAGER는 필요 없는 연관까지 항상 조회하고, JPQL 목록 조회에서는 오히려 N+1을 일으킴 → 기본은 LAZY, 필요한 곳만 Fetch Join

## 3. 상품 목록 조회와 N+1  

- 자세한 과정은 [til0928](til0928.md)에 정리, 오늘은 **왜 그렇게 되는지** 위주로 복습  

| 구분 | 구성 | 쿼리 수 |
| :--- | :--- | :---: |
| Before | 목록 1 + count 1 + 카테고리 5 + 판매자 1 + 이미지 12 + 찜 12 | 32 |
| After | 목록(JOIN FETCH) 1 + count 1 + 이미지 `IN` 1 + 찜 `GROUP BY` 1 | **4** |

- 카테고리·판매자가 12번이 아닌 이유: 같은 id는 **1차 캐시**에서 꺼내므로 **처음 보는 id**만 조회  

- 컬렉션 Fetch Join + 페이징 → `limit` 없이 전부 읽고 **메모리에서 페이징** (`HHH90003004` 경고)  

- Batch Size로 만든 `IN` 절은 개수가 모자라면 남는 자리를 `null`로 채워서 보냄  

- `getOrDefault(id, 0)`: 찜이 0개인 상품은 `GROUP BY` 결과에 행이 없어 `get()`이 `null` → `int`로 언박싱할 때 `NullPointerException`  

- `(:q IS NULL OR LOWER(p.title) LIKE ...)`: 검색어가 없으면 조건 자체를 무시하는 **선택적 필터** (`categoryId`도 같은 방식)  

- `countQuery`를 따로 작성해 count에는 불필요한 조인이 붙지 않게 함
