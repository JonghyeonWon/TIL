## 1. 인증과 인가 

### 1-1. 필터 체인 3개  

- `SecurityConfig`에 `SecurityFilterChain`을 3개 두고, 요청 URL에 맞는 **첫 번째 체인 하나만** 적용됨 (`@Order` 순서)  

    | 순서 | 대상 | 인증 방식 | 인증 실패 시 |
    | :---: | :--- | :--- | :--- |
    | 1 | `/api/**` | JWT (`STATELESS`, CSRF off) | 401 JSON (`AuthenticationEntryPoint`) |
    | 2 | `/admin/**` | 세션 + formLogin (CSRF on) | 302 → `/admin/login` |
    | 3 | 나머지 | 전부 `permitAll` | — |

- `/api` 체인은 세션을 만들지 않으므로 요청마다 `Authorization: Bearer <토큰>`을 보내야 함  

- 인증 실패는 컨트롤러까지 가기 전 **필터 단계**에서 끝나므로 `GlobalExceptionHandler`(advice)가 아니라 `AuthenticationEntryPoint`가 401 JSON을 직접 씀  

### 1-2. JWT 인증 흐름  

```
요청 → JwtAuthenticationFilter
        ├ 헤더에서 "Bearer " 뒤 토큰 추출
        ├ validateToken() — 서명·만료 검사
        ├ 통과: SecurityContext에 Authentication(principal = userId 문자열, ROLE_xxx) 저장
        └ 실패: 아무것도 저장하지 않고 다음 필터로 넘김
      → authorizeHttpRequests
        ├ permitAll 경로 → 통과
        └ authenticated 경로 + 인증 없음 → EntryPoint → 401
```

- 토큰이 틀리거나 만료돼도 필터는 **예외를 던지지 않고 그냥 통과**시킴 → 401 여부는 뒤의 `authorizeHttpRequests`가 경로 규칙으로 결정  

- `ExpiredJwtException`(토큰 만료)은 필터의 `catch`가 아니라 `validateToken()` 안에서 먼저 잡혀 `false`로 바뀜  

    ```java
    public boolean validateToken(String token) {
        try {
            parseClaims(token);
            return true;
        } catch (ExpiredJwtException e) {
            log.debug("만료된 토큰: {}", e.getMessage());
        } catch (JwtException | IllegalArgumentException e) {
            log.warn("유효하지 않은 토큰: {}", e.getMessage());
        }
        return false;
    }
    ```

- 그래서 **만료된 토큰**으로 요청하면  

    | 요청 | 결과 |
    | :--- | :--- |
    | `GET /api/products` (`permitAll`) | 200 — 비로그인 사용자로 처리 |
    | `POST /api/products` (`authenticated`) | 401 `AUTHENTICATION_REQUIRED` |

### 1-3. 토큰 위조 방지 — 서명(HS256)  

- JWT의 payload는 Base64로 인코딩돼 있을 뿐 **암호화된 것이 아님** → 누구나 디코딩해서 읽을 수 있음  

    - 그래서 payload에는 비밀번호 같은 민감 정보를 넣지 않음  

- payload의 `role`을 `ADMIN`으로 바꿔도 위조가 걸리는 이유는 **서버만 아는 secret으로 만든 서명(HS256)** 이 payload와 맞지 않기 때문  

    - `parseSignedClaims()`가 서명 검증에 실패 → `validateToken()`이 `false` → 인증 없음 → 401  

- BCrypt와 헷갈리지 않기  

    | 구분 | 용도 |
    | :--- | :--- |
    | HS256 서명 (secret key) | 토큰이 **서버가 발급한 그대로인지** 검증 |
    | BCrypt | **비밀번호**를 해시로 저장하고 로그인 시 비교 |

### 1-4. `CurrentUser`  

- 컨트롤러는 `SecurityContextHolder`를 직접 만지지 않고 `CurrentUser`의 두 메서드만 씀  

    - `id()`: 로그인 필수 API용, 없으면 401 `BusinessException`  
    - `idOrNull()`: 공개 API에서 "로그인한 사람 기준"이 필요할 때 (예: 상품 상세의 `wished`)  

- `"anonymousUser"` 체크를 지워도 응답은 똑같음  

    - `idOrNull()`에서 익명 사용자의 principal `"anonymousUser"`는 `Long.valueOf()`에서 `NumberFormatException` → `catch`에서 `Optional.empty()`로 바뀜  

### 1-5. `requestMatchers`의 `*`와 `**`  

- `*`는 **경로 한 칸(segment)**, `**`는 **여러 칸**과 매칭  

    | 패턴 | `/api/products/3` | `/api/products/3/similar` |
    | :--- | :---: | :---: |
    | `/api/products/*` | ⭕ | ❌ |
    | `/api/products/**` | ⭕ | ⭕ |

### 1-6. 관리자 체인(admin) 

- 관리자 페이지(`/admin`)에 로그인 성공하면 서버가 세션을 만들고 브라우저에 `JSESSIONID` 쿠키(번호표)를 줌 → 이후 요청은 번호표로 사용자를 찾음  

- 로그인 처리 흐름  

    ```
    POST /admin/login
      → UsernamePasswordAuthenticationFilter
      → DaoAuthenticationProvider (Boot 자동 구성)
      → CustomUserDetailsService.loadUserByUsername()
      → UserPrincipal 반환 → PasswordEncoder(BCrypt)로 비밀번호 비교
    ```

- `/api` 쪽 principal은 `String` userId이고, `UserPrincipal`/`CustomUserDetailsService`는 **`/admin` 로그인에서만** 사용됨  

- CSRF를 `/admin`에서만 켜는 이유: 판단 기준은 **브라우저가 인증 정보를 자동으로 보내는가**  

    | 체인 | 인증 정보 | 자동 전송 | CSRF |
    | :--- | :--- | :---: | :---: |
    | `/admin` | `JSESSIONID` 쿠키 | ⭕ (다른 사이트에서 보낸 요청에도 붙음) | 필요 |
    | `/api` | `Authorization` 헤더 | ❌ (JS가 직접 넣어야 함) | 불필요 |

- `@PreAuthorize("hasRole('ADMIN')")`는 **메서드 본문 실행 전**에 막음 → 메서드 안의 `try/catch`로는 처리 불가  

    - 이때 발생한 `AccessDeniedException`을 `AdminControllerExceptionHandler`의 `Exception.class` 핸들러가 받아버려서, 403이 아니라 "일시적인 오류" flash + Referer redirect가 됨

## 2. 상품 등록과 파일 저장  

### 2-1. multipart 요청  

- JSON과 파일을 한 요청에 보내기 위해 `multipart/form-data`로 받음  

    ```java
    @PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    @ResponseStatus(HttpStatus.CREATED)
    public ApiResponse<ProductDetailResponse> create(
            @RequestPart("product") @Valid ProductCreateRequest request,
            @RequestPart(value = "images", required = false) List<MultipartFile> images) {
        ...
    }
    ```

    - `product` 파트: JSON → `ProductCreateRequest`로 변환 후 `@Valid` 검증  
    - `images` 파트: 파일 목록, `required = false`라 없어도 됨 → 이때 `images`는 `null`  

- `categoryId`를 `@Pattern("\\d{1,18}")`로 먼저 검증하므로 서비스의 `Long.parseLong()`에는 숫자만 도달함  

### 2-2. `null`과 `isEmpty()`  

```java
List<MultipartFile> files =
        images == null ? List.of() : images.stream()
                .filter(f -> !f.isEmpty()).toList();
```

- `images == null`: `images` 파트 자체가 없음  

- `f.isEmpty()`: 파트는 왔지만 **파일 내용이 0바이트** (빈 목록이라는 뜻이 아님) → 파일 선택 없이 폼을 보낼 때 생길 수 있어서 걸러냄  

### 2-3. 파일은 DB 롤백이 안 됨  

- `@Transactional`은 **DB만** 되돌림 → 디스크에 이미 저장한 파일은 그대로 남음  

- 그래서 저장한 파일 이름을 모아 두고, 실패하면 직접 지운 뒤 예외를 다시 던짐  

    ```java
    List<String> storedNames = new ArrayList<>();
    try {
        for (MultipartFile file : files) {
            StoredFile stored = fileStorageService.store(file, FileStorageService.PRODUCTS);
            storedNames.add(stored.storedName());
            product.addImage(...);
        }
        productRepository.save(product);
    } catch (RuntimeException e) {
        storedNames.forEach(name -> fileStorageService.delete(FileStorageService.PRODUCTS, name));
        throw e;
    }
    ```

### 2-4. `FileStorageService.store()` 검사 순서  

1. 빈 파일 → `VALIDATION_ERROR`  
2. 5MB 초과 → `FILE_TOO_LARGE`  
3. 원본 이름에서 확장자 추출 → 허용 목록에 없으면 `FILE_TYPE_NOT_ALLOWED`  
4. 앞머리 바이트(**매직 넘버**)가 확장자와 맞는지 → 다르면 `FILE_TYPE_NOT_ALLOWED`  
5. `UUID.확장자`로 이름을 바꿔 저장  

- 저장 위치 허용 확장자는 `subdir`별로 다름 (`products`: 이미지만, `disputes`: 이미지 + pdf)  

### 2-5. UUID로 이름 바꾸기  

- 사용자가 준 이름을 그대로 쓰면 **이름 충돌**(덮어쓰기), 한글·특수문자 문제, 경로 조작 위험이 있음 → 저장 이름은 `UUID`, 원본 이름은 DB에만 보관  

- 저장 이름에 확장자를 남기는 이유는 나중에 파일을 내려줄 때 `Content-Type`을 정하기 위해서 (`contentType()` 메서드)  

### 2-6. 매직 넘버 검사  

- 확장자는 이름만 바꾸면 되므로 믿지 않음 → 파일 앞 12바이트를 읽어 실제 형식 확인  

    | 형식 | 시그니처 |
    | :--- | :--- |
    | jpg | `FF D8 FF` |
    | png | `89 50 4E 47 0D 0A 1A 0A` |
    | webp | `RIFF` .... `WEBP` |
    | pdf | `%PDF-` |

- `mark()` → 앞부분 읽기 → `reset()`으로 스트림을 처음으로 되돌린 뒤 전체를 복사  

### 2-7. 경로 조작(Path Traversal) 방어  

- 원본 이름에서 마지막 `/`, `\` 뒤만 남겨 `../../etc/passwd` 같은 경로를 잘라냄  

- `load()`/`delete()` 메서드는 `normalize()`로 `..`을 정리한 뒤 `startsWith(directory)`로 **업로드 폴더 밖이면 거부**  

    ```java
    Path target = directory.resolve(storedName).normalize();
    if (!target.startsWith(directory)) {
        throw new BusinessException(ErrorCode.FILE_STORAGE_ERROR);
    }
    ```

### 2-8. 조용한 삭제  

- `delete()`는 파일이 없거나 삭제에 실패해도 예외를 던지지 않음  

- 롤백용으로 부르는 메서드이므로, 삭제 실패로 원래 예외가 가려지는 것보다 **고아 파일 하나가 남는 편이 나음**
