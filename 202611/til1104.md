## 1. Kubernetes 객체 전체 흐름  

- 객체마다 맡은 역할이 나뉘어 있고, 라벨(label)과 셀렉터(selector)로 서로를 찾아서 연결  

```
Deployment ──관리──▶ ReplicaSet ──관리──▶ Pod × N
 (버전·이력)          (개수 유지)          (컨테이너 실행)
                                          ▲
Service ──── selector(app: boot-kube) ────┘  (고정 주소로 Pod에 접근)

ConfigMap / Secret ──환경 변수·파일로 주입──▶ Pod
```

| 객체 | 한 줄 역할 |
| :--- | :--- |
| Pod | 컨테이너를 담는 최소 실행 단위 |
| ReplicaSet | Pod를 정해진 개수만큼 유지 |
| Deployment | ReplicaSet을 관리하며 버전 업데이트·롤백 제공 |
| Service | 바뀌는 Pod들 앞에 고정된 접속 주소 제공 |
| ConfigMap | 일반 설정값 저장 |
| Secret | 비밀번호 같은 민감 정보 저장 |

---

## 2. Pod  

- 컨테이너를 담는 최소 단위 객체 → k8s는 컨테이너를 직접 다루지 않고 Pod 단위로 배포·관리  

- 같은 Pod 안의 컨테이너는 IP와 볼륨을 공유 → 서로 `localhost`로 통신  

### 2-1. Pod는 일회용  

- Pod는 죽으면 되살아나는 것이 아니라, 새 Pod가 새 이름·새 IP로 만들어짐  

- Pod만 단독으로 만들면 죽었을 때 다시 만들어 줄 주체가 없음 → 실무에서는 Pod를 직접 만들지 않고 Deployment로 관리  

| 구분 | 특징 |
| :--- | :--- |
| 단독 Pod | 삭제·장애 시 그대로 사라짐 |
| Deployment가 만든 Pod | 사라지면 ReplicaSet이 즉시 새 Pod 생성 |

---

## 3. ReplicaSet  

- Pod를 정해진 수(`replicas`)만큼 복제하고 그 개수를 계속 유지하는 객체  

- 현재 Pod 수를 계속 확인 → 원하는 수보다 적으면 생성, 많으면 삭제  

### 3-1. 구성 요소  

| 항목 | 의미 |
| :--- | :--- |
| `replicas` | 유지할 Pod 개수 |
| `selector` | 어떤 라벨을 가진 Pod를 관리할지 지정 |
| `template` | Pod가 부족할 때 새로 만들 Pod 설계도 |

- `selector`의 라벨과 `template`의 라벨이 반드시 같아야 함 → 자기가 만든 Pod를 라벨로 찾아서 개수를 셈  

### 3-2. 한계  

- 개수 유지만 담당 → 이미지 버전을 바꿔도 이미 떠 있는 Pod는 그대로  

- 버전 교체·이력 관리 기능이 없음 → 직접 사용하지 않고 Deployment를 통해 사용  

---

## 4. Deployment  

- ReplicaSet을 한 단계 위에서 관리하는 객체 → Pod의 버전 업데이트, 이력 관리, 특정 버전으로 롤백 기능 제공  

- Deployment 생성 → ReplicaSet 자동 생성 → ReplicaSet이 Pod 생성

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: boot-kube
spec:
  replicas: 3                 # Pod 3개 유지
  selector:
    matchLabels:
      app: boot-kube          # 이 라벨을 가진 Pod를 관리
  template:                   # Pod 설계도
    metadata:
      labels:
        app: boot-kube
    spec:
      containers:
        - name: bootapp
          image: bmsvega2k/boot-kube:0.1
```

### 4-1. 롤링 업데이트(Rolling Update)  

- 이미지 버전을 바꾸면 새 ReplicaSet을 만들고, 새 Pod를 하나씩 늘리면서 이전 Pod를 하나씩 줄임  

- 항상 일부 Pod가 살아 있음 → 서비스 중단 없이 버전 교체(무중단 배포)  

```
image 0.1 → 0.2 변경

ReplicaSet(0.1)  [Pod][Pod][Pod] → [Pod][Pod] → [Pod] → (0개, 삭제 안 하고 남겨둠)
ReplicaSet(0.2)                  → [Pod]      → [Pod][Pod] → [Pod][Pod][Pod]
```

### 4-2. 이력 관리와 롤백  

- 업데이트 후에도 이전 ReplicaSet을 Pod 0개 상태로 남겨둠 → 이것이 곧 버전 이력(revision)  

- 롤백 = 이전 ReplicaSet의 Pod 수를 다시 늘리고, 현재 ReplicaSet을 줄이는 것  

| 명령어 | 역할 |
| :--- | :--- |
| `kubectl rollout status` | 업데이트 진행 상황 확인 |
| `kubectl rollout history` | 버전 이력 확인 |
| `kubectl rollout undo` | 직전 버전으로 롤백 |
| `kubectl rollout undo --to-revision=N` | 특정 버전으로 롤백 |

### 4-3. 세 객체 비교  

| 구분 | Pod | ReplicaSet | Deployment |
| :--- | :--- | :--- | :--- |
| 자동 복구 | X | O | O |
| 개수 유지·확장 | X | O | O |
| 무중단 업데이트 | X | X | O |
| 이력·롤백 | X | X | O |

## 5. Service  

### 5-1. 필요한 이유  

- Pod는 새로 만들어질 때마다 IP가 바뀜 → Pod IP로 직접 접속하면 Pod가 교체되는 순간 연결이 끊김  

- Pod가 여러 개면 어느 Pod로 보낼지도 정해야 함  

- 고정된 IP와 이름을 가진 Service를 만들고, Service를 통해서 Pod에 접근하는 방식 사용  

```
클라이언트 ──▶ Service (고정 IP, 이름: boot-kube-svc)
                 │ selector: app=boot-kube
       ┌─────────┼─────────┐
     [Pod]     [Pod]     [Pod]   ← IP가 바뀌어도 라벨로 다시 찾음
```

- Service는 `selector` 라벨과 일치하는 Pod 목록을 계속 갱신 → 요청을 여러 Pod에 나눠 보냄(로드밸런싱)  

- 클러스터 내부 DNS → 다른 Pod에서 Service 이름(`boot-kube-svc`)으로 접속 가능

### 5-2. Service 종류  

| 종류 | 접근 범위 | 특징 |
| :--- | :--- | :--- |
| ClusterIP | 클러스터 내부 | 기본값, 내부 전용 고정 IP → 백엔드·DB처럼 외부 노출이 필요 없는 곳 |
| NodePort | 외부 (`노드IP:nodePort`) | 모든 노드의 같은 포트를 열어 Service로 연결 |
| LoadBalancer | 외부 (로드밸런서 IP) | 로드밸런서를 자동 생성해 연결 |

- 세 종류는 차례로 쌓이는 구조 → LoadBalancer는 내부적으로 NodePort를, NodePort는 ClusterIP를 함께 만듦  

```
LoadBalancer ──▶ NodePort(노드IP:30080) ──▶ ClusterIP ──▶ Pod
  (클라우드)         (외부 접속 입구)          (내부 고정 IP)
```

## 6. ConfigMap과 Secret  

- 설정값을 이미지 안에 넣으면 값이 바뀔 때마다 이미지를 다시 빌드해야 함 → 설정을 별도 객체로 분리해 Pod 실행 시 주입  

- Docker에서 `--env-file .env`로 분리했던 것과 같은 개념을 k8s 객체로 관리  

### 6-1. ConfigMap  

- 필요한 설정값(환경 변수, 설정 파일 내용)을 key-value로 저장하는 객체  

- DB 주소, 포트, 프로파일처럼 노출돼도 상관없는 일반 설정 저장  

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: mariadb-svc        
  DB_PORT: "3306"           
```

### 6-2. Secret  

- 비밀번호, API 키 같은 민감 정보를 저장하는 객체 → 값을 Base64로 인코딩하여 저장  

- Base64는 누구나 디코딩 가능하므로 Secret 자체를 Git에 올리면 안 됨  

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  MARIADB_PASSWORD: MTIzNA==  # "1234"를 Base64로 인코딩한 값
```

| 구분 | ConfigMap | Secret |
| :--- | :--- | :--- |
| 저장 대상 | 일반 설정값 | 비밀번호·키 등 민감 정보 |
| 저장 형태 | 평문 | Base64 인코딩 |
| 출력 시 | `kubectl describe`에 값 그대로 표시 | 값을 숨기고 크기만 표시 |
| 권한 관리 | 일반 | 접근 권한을 따로 제한해서 관리 |
