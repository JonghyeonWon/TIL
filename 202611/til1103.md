## 1. FastAPI + LLM REST API 배포  

- LangChain 체인(`prompt | llm`)을 FastAPI로 직접 serve → REST API로 LLM 기능 제공  

- API 키 같은 비밀 값은 이미지에 넣지 않고 실행 시점에 `--env-file .env`로 전달  

### 1-1. SSE(Server-Sent Events)  

- 서버 → 클라이언트 단방향으로, 연결 하나를 유지한 채 데이터를 조각조각 계속 보내는 방식  

- LLM은 답변을 토큰 단위로 생성 → 다 만들어질 때까지 기다리지 않고 생성되는 대로 보여줄 수 있음 

```python
async def event_generator():
    async for chunk in chain.astream({"question": q}):
        yield f"data: {json.dumps({'token': chunk.content}, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"

return StreamingResponse(event_generator(), media_type="text/event-stream")
```

- `ensure_ascii=False`: 한글을 `\uXXXX`로 바꾸지 않고 그대로 전송  

### 1-2. Dockerfile  

```dockerfile
FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
WORKDIR /app
COPY pyproject.toml uv.lock .python-version ./
RUN uv sync --locked --no-dev
COPY 010_FastAPI_Basic.py 010_FastAPI_stream_test.html ./
ENV PATH="/app/.venv/bin:$PATH"
HEALTHCHECK CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
CMD ["uvicorn", "010_FastAPI_Basic:app", "--host", "0.0.0.0", "--port", "8000"]
```

- `--host 0.0.0.0`: `127.0.0.1`은 컨테이너 자기 자신만 접속 가능 → 컨테이너 밖에서 접속할 때 모든 주소에서 받도록 설정

## 2. Gradio + RAG Chatbot 배포  

### 2-1. RAG(Retrieval-Augmented Generation)  

- LLM이 학습하지 않은 문서(PDF 등)를 검색해서 프롬프트에 함께 넣어주고, 그 내용을 근거로 답하게 하는 방식  

- 문서 내용만 근거로 답하도록 프롬프트에서 제한 → 할루시네이션 감소  

```
[인덱싱 - 문서 등록마다]
PDF ─▶ PyPDFLoader ─▶ TextSplitter ─▶ 임베딩 ─▶ FAISS(벡터 저장소)
       (페이지 단위)    (청크 분할)     (벡터화)

[질의 - 질문마다]
질문 ─▶ 임베딩 ─▶ 유사 청크 k개 검색 ─▶ context로 프롬프트에 삽입 ─▶ LLM ─▶ 답변 + 출처
```

| 단계 | 역할 |
| :--- | :--- |
| Chunk 분할 | 긴 문서를 작은 조각으로 분할, `chunk_overlap`으로 앞뒤 문맥이 끊기지 않게 겹침 |
| Embedding | 텍스트를 의미를 담은 벡터로 변환 |
| Vector Store | 벡터를 저장하고 질문 벡터와 가까운 청크 검색 |
| Retriever | 질문 → 유사 청크 k개를 꺼내는 검색기 |

### 2-2. Gradio  

- Python 코드만으로 채팅 UI같은 웹 화면을 만들어주는 라이브러리  

- `demo.launch()`가 웹 서버까지 띄움 → uvicorn이 아닌 `python 파일.py`로 실행

## 3. Kubernetes(k8s)

### 3-1. 개념  

- 여러 노드에 걸쳐 컨테이너를 자동으로 배포·확장·관리하는 컨테이너 오케스트레이션 도구   

- Docker Compose는 서버 1대 안의 여러 컨테이너 관리, Kubernetes는 여러 서버로 이루어진 클러스터 전체를 관리  

- 선언형 방식: 원하는 상태를 YAML로 선언 → k8s가 현재 상태를 계속 원하는 상태로 맞춤  

### 3-2. 장점  

| 장점 | 내용 |
| :--- | :--- |
| 자동 복구(Self-healing) | 컨테이너가 죽으면 자동으로 다시 생성 |
| 확장(Scaling) | `replicas` 숫자만 바꾸면 Pod 수가 늘거나 줄어듦 |
| 로드밸런싱 | Service가 여러 Pod에 트래픽을 나눠줌 |
| 무중단 배포 | Rolling Update로 이전 버전을 하나씩 교체, 문제 시 롤백 |
| 서비스 디스커버리 | Pod IP가 바뀌어도 Service 이름으로 접속 |
| 이식성 | 로컬(Minikube), 온프레미스, 클라우드(EKS, GKE, AKS) 어디서든 같은 YAML 사용 |

## 4. Kubernetes 구성 요소  

```
kubectl ──▶ Control Plane (api server, etcd, scheduler, controller-manager로 구성)
                 │ 지시
      ┌──────────┴──────────┐
 Worker Node            Worker Node     (kubelet, kube-proxy, Container Runtime)
 [Pod][Pod]             [Pod][Pod]
```

### 4-1. Control Plane(Master Node)

| 구성 요소 | 역할 |
| :--- | :--- |
| api server | 클러스터의 출입구, kubectl을 포함한 모든 요청을 받아 가장 먼저 처리 |
| etcd | 클러스터의 모든 정보를 저장하는 key-value 저장소 |
| kube-scheduler | 새 Pod를 어느 Worker Node에 배치할지 결정 |
| kube-controller-manager | 현재 상태를 원하는 상태로 맞추는 컨트롤러들 실행 |

### 4-2. Worker Node

| 구성 요소 | 역할 |
| :--- | :--- |
| kubelet | server와 소통 → api server 지시대로 Pod를 실행하고 상태 보고 |
| kube-proxy | 네트워크 규칙 관리 → Service로 들어온 트래픽을 Pod로 전달 |
| Container Runtime | 실제로 컨테이너를 실행 |

## 5. Kubernetes 객체  

- 원하는 상태를 YAML로 작성해 `kubectl apply -f`로 등록  

- 공통 구조: `apiVersion`(API 버전), `kind`(객체 종류), `metadata`(이름·라벨), `spec`(원하는 상태)  

### 5-1. Pod  

- k8s에서 배포할 수 있는 가장 작은 단위 → 컨테이너를 직접 실행하지 않고 Pod로 감싸서 실행  

- Pod 안에 컨테이너는 한 개일 수도, 여러 개일 수도 있음  

- 같은 Pod 안의 컨테이너는 네트워크(IP)와 볼륨을 공유 → 서로 `localhost`로 통신  

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: boot-kube           # Pod 이름
  labels:
    app: boot-kube          # 라벨 → Deployment, Service가 Pod를 찾는 기준
spec:
  containers:
    - name: bootapp         # 컨테이너 이름
      image: bmsvega2k/boot-kube:0.1
```
