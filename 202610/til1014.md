## 1. 보안의 기본 개념  

### 1-1. 정보보안의 3요소 (CIA)  

| 요소 | 뜻 | 깨지는 예 |
| :--- | :--- | :--- |
| Confidentiality (기밀성) | 허가된 사람만 정보를 볼 수 있음 | 개인정보·비밀번호 해시 유출 |
| Integrity (무결성) | 허가 없이 정보가 바뀌지 않음 | 남의 데이터 수정, 쿠폰 할인율 변조 |
| Availability (가용성) | 필요할 때 서비스를 쓸 수 있음 | DoS, `DROP TABLE`로 데이터 삭제 |

### 1-2. 보안 설계의 핵심 원칙  

| 원칙 | 뜻 |
| :--- | :--- |
| Defense in Depth (심층 방어) | 한 가지 방어에 의존하지 않고 여러 겹으로 쌓음 |
| Least Privilege (최소 권한) | 꼭 필요한 권한만 부여 |
| Secure by Default (기본값 안전) | 아무 설정을 안 해도 안전한 상태가 기본 상태 / 열어야 할 것만 명시적으로 허용 |
| Fail Securely (안전한 실패) | 오류가 나면 거부하는 쪽으로 실패 + 내부 정보 노출 x |
| Never Trust Input | 클라이언트가 보낸 값은 모두 조작될 수 있다고 가정하고 서버에서 검증 |
| Zero Trust | 내부망·로그인 사용자라도 믿지 않고, 요청마다 인증·인가를 확인 |

### 1-3. 보안의 종류  

| 종류 | 대상 |
| :--- | :--- |
| 물리 보안 | 출입 통제, 서버실, 장비 도난 |
| 네트워크 보안 | 방화벽, IDS/IPS, 트래픽 암호화 |
| 시스템(서버/OS) 보안 | 계정·권한 관리, 패치, 불필요한 서비스 제거 |
| 애플리케이션 보안 | 백엔드(인젝션, 인가)·프론트엔드(XSS 등) 코드의 취약점 |
| 공급망 보안 | 외부 라이브러리·빌드 도구의 취약점·오염 (SBOM, CVE) |
| AI/LLM 보안 | 프롬프트 인젝션, 에이전트의 과도한 권한, 민감정보 유출 |

### 1-4. AI를 활용한 공격 기법  

| 기법 | 내용 |
| :--- | :--- |
| 자동화 정찰·취약점 탐색 | AI가 대상의 엔드포인트·버전 정보를 수집하고 취약점을 빠르게 탐색 |
| 크리덴셜 스터핑 | 다른 곳에서 유출된 아이디/비밀번호 조합을 대량으로 자동 대입 |
| AI 에이전트 자율 침투 | 에이전트가 정찰 → 공격 → 결과 확인 루프를 스스로 반복 |
| AI 생성 피싱 | 문법·말투가 자연스러운 맞춤형 피싱 메일·메시지 생성 |

- AI로 인해 공격의 속도와 규모가 커짐에 따라 로그인 시도 제한, 속도 제한, 로깅·모니터링의 중요성이 커짐

## 3. SQL Injection

- 입력값에 SQL 구문을 끼워 넣어 의도하지 않은 DB 명령을 실행시키는 공격  

- 사용자 입력을 데이터가 아니라 쿼리 구문으로 인식하기 때문에 발생  

| 유형 | 결과 확인 방식 |
| :--- | :--- |
| UNION 기반 | 응답 화면에 탈취한 데이터를 직접 실어 봄 |
| 오류 기반 | DB 오류 메시지에서 정보를 알아냄 |

### 3-1. 공격 원리  

```java
// [취약한 경우] 입력을 문자열로 결합
String sql = "SELECT student_id, name, student_number FROM students "
           + "WHERE name LIKE '%" + name + "%'";
```

```sql
-- name값이 %' UNION SELECT id, email, password FROM user_info # 인 경우
SELECT student_id, name, student_number FROM students
WHERE name LIKE '%%' UNION SELECT id, email, password FROM user_info #%'
```

- `'`가 문자열을 닫고, `UNION SELECT`가 새 구문이 되며, `#`이 뒤에 남은 `%'`를 주석 처리함으로써 새로운 쿼리 구문이 됨

- UNION 성립 조건: 컬럼 수가 같고, 타입이 호환되어야 함 → 모자라면 `1`, `NULL`로 채움  

- 단계별 공격 과정

| 단계 | 페이로드 예 | 목적 |
| :--- | :--- | :--- |
| 항상 참 | `%' OR '1'='1` | 조건을 무력화해 전체 조회 |
| 컬럼 수 확인 | `%' UNION SELECT 1,2,3 #` | 숫자 행이 나오면 컬럼 수 일치 |
| 구조 탐색 | `information_schema.tables / columns` | 테이블·컬럼 이름 파악 |
| 데이터 탈취 | `UNION SELECT id, email, password FROM user_info` | 계정·비밀번호 해시 유출 |

### 3-2. 방어: 파라미터 바인딩  

- 쿼리 구조는 코드로 고정하고, 입력은 자리표시자(`?`, `:name`)를 통해 전달 → 따옴표·UNION이 들어와도 검색어로 취급됨

```java
// [안전] JdbcTemplate ? 바인딩
jdbcTemplate.queryForList("SELECT ... FROM students WHERE name LIKE ?", "%" + name + "%");

// [안전] JPA 네이티브 :name 바인딩
entityManager.createNativeQuery("... WHERE name LIKE :name")
             .setParameter("name", "%" + name + "%");

// [안전] JPA 메서드 쿼리 - 문자열 조립 자체가 없음
studentRepository.findByNameContainingIgnoreCase(name, pageable);
```

### 3-3. 심층 방어  

| 순위 | 대책 | 역할 |
| :--- | :--- | :--- |
| 근본 | 파라미터 바인딩 / ORM 메서드 쿼리 | 인젝션 자체를 성립시키지 않음 |
| 보조 | 입력 검증, 타입 강제 | 허용된 형태만 통과 (`@Valid`, `Long id`) |
| 피해 축소 | DB 계정에 최소 권한 제공 | 뚫려도 할 수 있는 일을 줄임 |
| 피해 축소 | 오류 메시지 숨김 | 오류 기반 인젝션의 단서 차단 |
| 피해 축소 | 비밀번호 해시 저장 (BCrypt) | 탈취돼도 즉시 악용 어려움 |

## 4. Broken Access Control / IDOR

- IDOR(Insecure Direct Object Reference): 로그인한 사용자가 요청한 리소스가 본인 것인지 서버가 검사하지 않아, `{id}`만 바꾸면 남의 데이터에 접근되는 취약점  

```
user(id=2)로 로그인 → GET /api/idor/profiles/1 (id만 변경) → 다른 사용자의 정보를 별도 검사 없이 반환
```

- 방어: 요청자와 리소스 소유자를 대조해 본인 또는 관리자만 허용 → 본인도 관리자도 아니면 `403`(권한 없음)  

```java
@PreAuthorize("hasRole('ADMIN') or #id == principal.userInfo.id")
```
