> BE-C 담당: 상품 목록·상세·등록, 찜 추가·해제 (+ 관리자 검수 화면용 검수 대기 목록 지원)

## 1. 상품 목록 — 검색·카테고리·페이징  

### 1-1. 파라미터 검증  

```java
@GetMapping
public ApiResponse<PageResponse<ProductSummaryResponse>> list(
        @RequestParam(required = false) String q,
        @RequestParam(required = false) Long categoryId,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "12") int size) {

    if (page < 0 || size < 1) throw new BusinessException(ErrorCode.VALIDATION_ERROR);
    int pageSize = Math.min(size, 100);
    ...
}
```

- `page`가 음수이거나 `size`가 0 이하면 **400 `VALIDATION_ERROR`**  

- `size`는 에러를 내지 않고 **최대 100으로 잘라냄** → `size=10000` 같은 요청으로 DB 전체를 읽는 것을 막음  

    - 100은 N+1 개선의 `default_batch_fetch_size: 100`과 같은 값 → 어떤 페이지 크기든 이미지 batch 쿼리 1번으로 끝남 (N+1 문서 참고)  

- `categoryId`에 숫자가 아닌 값이 오면 `Long` 변환 실패(`MethodArgumentTypeMismatchException`) → 400 `VALIDATION_ERROR`  

### 1-2. 검색어 정규화  

```java
String normalizedQ = (q == null || q.isBlank()) ? null : q.trim().toLowerCase();
```

- 프론트는 검색어를 **원문 그대로** 보내고, 정규화는 서버가 한 곳에서만 함  

- 공백만 있는 검색어(`"   "`)는 `null`로 바꿔 **검색 조건 없음**으로 처리  

- 앞뒤 공백 제거 + 소문자화 → DB 쪽도 `LOWER(p.title)`로 비교해서 대소문자 구분 없이 검색  

### 1-3. 조건이 있을 때만 거는 JPQL  

```java
"WHERE p.status = :status " +
"AND (:q IS NULL OR LOWER(p.title) LIKE CONCAT('%', :q, '%')) " +
"AND (:categoryId IS NULL OR p.category.id = :categoryId) " +
"ORDER BY p.createdAt DESC, p.id DESC"
```

- `:q IS NULL OR ...` 패턴: 파라미터가 `null`이면 조건 전체가 참이 되어 **조건이 없는 것과 같음**  

- 검색만 / 카테고리만 / 둘 다 / 둘 다 없음 4가지 경우를 **쿼리 하나**로 처리 (메서드를 4개 만들 필요 없음)  

- `status`는 서비스에서 항상 `ON_SALE`을 넘김 → 목록에는 **판매중 상품만** 노출 (검수대기·반려 상품은 안 보임)  

### 1-4. 페이지 응답  

- `Page<Product>` → `pages.map(...)`으로 `Page<ProductSummaryResponse>` 변환 → `PageResponse.from()`으로 공통 형식에 담음  

    ```json
    "page": { "number": 0, "size": 12, "totalElements": 15, "totalPages": 2,
              "first": true, "last": false, "numberOfElements": 12 }
    ```

## 2. 상품 상세 — 로그인 여부에 따라 달라지는 `wished`  

### 2-1. 공개 API인데 로그인 사용자가 필요한 경우  

- 상세 조회는 **비로그인도 가능**하지만, 응답의 `wished`(내가 찜했는지)는 로그인한 사람 기준이어야 함  

- 로그인 사용자 id를 꺼내는 공용 유틸 `CurrentUser`의 두 메서드를 상황에 맞게 사용  

    | 메서드 | 로그인 안 했을 때 | 사용처 |
    | :--- | :--- | :--- |
    | `CurrentUser.id()` | 401 `AUTHENTICATION_REQUIRED` | 상품 등록, 찜 (로그인 필수) |
    | `CurrentUser.idOrNull()` | `Optional.empty()` | 상품 상세 (공개) |

    ```java
    @GetMapping("/{id}")
    public ApiResponse<ProductDetailResponse> detail(@PathVariable Long id) {
        ProductDetailResponse detailResponse =
                productService.getDetail(id, CurrentUser.idOrNull().orElse(null));
        ...
    }
    ```

- 비로그인 요청도 Security가 `"anonymousUser"`라는 익명 인증을 넣어 주므로, `idOrNull()`은 이 경우도 **로그인 안 함**으로 판단  

### 2-2. `wished` 계산  

```java
boolean wished = viewerId != null
        && wishRepository.existsByUserIdAndProductId(viewerId, product.getId());
```

- `&&`의 **단락 평가**: `viewerId`가 `null`이면 뒤의 DB 조회 자체를 하지 않고 `false`  

### 2-3. 응답 형태

- **사진 전체**를 `images` 배열로 내려줌 (0장이면 `null`이 아니라 `[]`)  

- 사진 URL은 파일 경로가 아니라 **API 경로**로 만들어 줌 → `"/api/products/{상품id}/images/{이미지id}"`  

- 에러  

    | 상황 | 응답 |
    | :--- | :--- |
    | 없는 상품 id | 404 `PRODUCT_NOT_FOUND` |
    | 숫자가 아닌 id (`/api/products/abc`) | 400 `VALIDATION_ERROR` |

## 3. 상품 등록 — 입력값 검증과 판매자 지정  

### 3-1. 요청 DTO 검증  

```java
public record ProductCreateRequest(
        @NotBlank @Size(max = 100) String title,
        @NotBlank @Size(max = 2000) String description,
        @NotNull @Positive Long priceKrw,
        @NotBlank @Pattern(regexp = "S|A|B|C") String conditionGrade,
        @NotBlank @Pattern(regexp = "\\d{1,18}") String categoryId
) { }
```

- 검증은 **엔티티가 아니라 DTO**에 걸어서 서비스 로직 전에 걸러냄  

- `conditionGrade`를 enum이 아니라 **String + `@Pattern`**으로 받는 이유  

    - enum 타입으로 받으면 `"Z"` 같은 값은 JSON 변환 단계에서 실패 → 어느 필드가 틀렸는지(`fields`) 없이 400만 나감  

    - String으로 받고 `@Pattern`으로 검사하면 `fields: [{ name: "conditionGrade", message: ... }]`로 **화면이 입력칸 아래에 오류를 띄울 수 있음**  

- `categoryId`도 같은 이유로 String + `@Pattern("\\d{1,18}")` → 서비스의 `Long.parseLong()`에는 숫자만 도달  

- 형식은 맞지만 존재하지 않는 카테고리 id → **400 `VALIDATION_ERROR`** (요청 URL의 자원이 아니라 입력값이 잘못된 것이므로 404가 아님)  

### 3-2. 판매자는 요청이 아니라 토큰에서  

```java
Long sellerId = CurrentUser.id();
ProductDetailResponse response = productService.create(sellerId, request, images);
```

- 요청 본문으로 `sellerId`를 받으면 **남의 이름으로 상품을 올릴 수 있음** → JWT에서 꺼낸 id만 사용  

- 사진은 `images` 파트(0~5장)로 함께 받음 → 파일 저장·실패 시 저장한 파일 삭제는 til0930 참고  

### 3-3. 등록 직후 상태  

- `Product` 생성자에서 `status = INSPECTING`으로 고정 → 등록한 사람이 상태를 정할 수 없음  

- 응답은 **201 Created** + 상세와 같은 형태, `status`는 항상 `INSPECTING`  

- 등록 직후 목록에 안 보이는 것이 정상 (관리자 검수 후 `ON_SALE`)

## 4. 찜 추가·해제  

### 4-1. API 형태  

| 요청 | 성공 | 실패 |
| :--- | :--- | :--- |
| `POST /api/products/{id}/wishes` | 201 | 409 `WISH_ALREADY_EXISTS` · 404 `PRODUCT_NOT_FOUND` |
| `DELETE /api/products/{id}/wishes` | 200 | 404 `WISH_NOT_FOUND` |

- 응답: `{ "productId", "wished", "wishCount" }` → 프론트가 하트 상태와 찜 수를 **응답값으로 바로 갱신**  

### 4-2. 중복 찜 2단계 방어  

```java
if (wishRepository.existsByUserIdAndProductId(userId, productId)) {
    throw new BusinessException(ErrorCode.WISH_ALREADY_EXISTS);
}
...
try {
    wishRepository.save(wish);
} catch (DataIntegrityViolationException e) {
    throw new BusinessException(ErrorCode.WISH_ALREADY_EXISTS);
}
```

- 1단계 `exists` 검사만으로는 부족 → 하트를 **빠르게 두 번** 누르면 두 요청이 동시에 검사를 통과할 수 있음  

    | 시점 | 요청 A | 요청 B |
    | :--- | :--- | :--- |
    | 1 | `exists` → 없음 | |
    | 2 | | `exists` → 없음 |
    | 3 | `insert` 성공 | |
    | 4 | | `insert` → **고유 제약 위반** |

- 2단계: DB의 고유 제약 `uk_wishes_user_product(user_id, product_id)`가 최후의 방어선 → 위반 예외(`DataIntegrityViolationException`)를 잡아서 500 대신 **409**로 바꿈  

- `save()` 줄에서 바로 예외를 잡을 수 있는 이유: id 전략이 `IDENTITY`라 id를 받으려면 **`save()` 순간 `INSERT`가 실행됨** (커밋 시점까지 미뤄지지 않음)

## 5. 검수 대기 목록 — 기존 쿼리 재사용  

- 관리자 검수 화면(BE-B)이 `INSPECTING` 상품 목록을 요청 → 새 쿼리를 만들지 않고 목록 쿼리를 재사용  

    ```java
    List<Product> products = productRepository.findProductsWithOptions(
            ProductStatus.INSPECTING, null, null, Pageable.unpaged()
    ).getContent();
    ```

- `status`만 바꾸고, `q`·`categoryId`는 `null`(조건 없음), `Pageable.unpaged()`로 **페이징 없이 전체**  

- 1-3에서 조건을 `:q IS NULL OR ...`로 만들어 둔 덕분에 그대로 재사용 가능  

- 관리자 화면은 서버 렌더링(Thymeleaf)이라 REST 컨트롤러 없이 **서비스 메서드만** 제공
