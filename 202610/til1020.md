## 1. 소프트웨어 공급망 실패 (Software Supply Chain Failures)  

- 공급망: `pom.xml`, `package.json`등에서 직접 선언한 라이브러리 + 그 라이브러리가 함께 끌고 오는 전이 의존성 전체

### 1-1. CVE (Common Vulnerabilities and Exposures)  

- 공개적으로 알려진 취약점에 부여되는 고유 식별번호 

- 형식: `CVE-연도-번호` (예: `CVE-2021-44228` = Log4Shell, log4j2 원격코드실행 취약점)  

- 심각도는 CVSS 점수(0~10)로 매기고, NVD(National Vulnerability Database)에서 조회  

### 1-2. SBOM (Software Bill of Materials)  

- 애플리케이션에 포함된 모든 구성요소(라이브러리·버전·라이선스)의 목록  

- 새 CVE가 발견되었을 때 우리 앱이 그 라이브러리를 쓰는지를 즉시 확인할 수 있는 목록  

```bash
# CycloneDX 플러그인으로 SBOM 생성
./mvnw org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
```

| 생성 파일 | 내용 |
| :--- | :--- |
| `target/bom.json` | JSON 형식 SBOM |
| `target/bom.xml` | XML 형식 SBOM |

### 1-3. 취약점 스캔  

- SBOM과 CVE 데이터베이스(NVD)를 대조하는 작업  

```
SBOM  ──대조──▶ CVE DB (NVD)
└──── 취약점 스캔 도구 ────┘
            ▼
이 라이브러리가 CVE-XXXX에 취약 → 업데이트 필요
```

## 2. 로그인 시도 제한 (Brute Force 방어)  

- 로그인 시도 횟수 제한이 없으면 Burp Intruder 같은 도구로 비밀번호 후보를 초당 수십~수백 번 대입 가능  

- 서버 입장에서는 정상 로그인 요청과 비정상 로그인 요청을 구분 불가

| 공격 | 내용 |
| :--- | :--- |
| 무차별 대입 (Brute Force) | 가능한 모든 조합을 순서대로 시도 |
| 사전 공격 (Dictionary Attack) | 자주 쓰이는 비밀번호 목록을 대입 |
| 크리덴셜 스터핑 (Credential Stuffing) | 다른 사이트에서 유출된 계정 정보를 그대로 대입 |

### 2-1. 계정 잠금 원리  

- 로그인 실패 횟수를 저장하고, 임계치를 넘으면 계정을 일정 시간 잠금

```java
// UserInfo 엔티티
private int failedLoginCount;   // 연속 로그인 실패 횟수 (성공 시 0으로 초기화)
private Instant lockedUntil;    // 이 시각 이전까지는 비밀번호가 맞아도 거부 
```

```properties
# .properties
# 5회가 실패 임계점
login.lockout.max-attempts=5
# 300초 동안 잠금
login.lockout.duration-seconds=300
```

| 메서드 (`LoginAttemptService`) | 역할 |
| :--- | :--- |
| `assertNotLocked()` | 잠겨 있으면 비밀번호 검증 전에 `LockedException`으로 즉시 차단 |
| `onFailure()` | 실패 횟수 +1, 임계치 도달 시 `lockedUntil` 설정 + 로그 |
| `onSuccess()` | 실패 횟수와 잠금을 초기화 |

### 2-2. 공통 지점에 적용하기  

- 처음엔 REST 로그인(`/api/userinfos/login`) 컨트롤러에만 적용 → 화면 로그인(`/login-process`)은 컨트롤러를 거치지 않아 잠금이 우회되는 사각지대 발생  

- 두 로그인 경로 모두 `AuthenticationManager` → `DaoAuthenticationProvider`를 공통으로 거친다는 점을 이용  

```
[화면 로그인 /login-process] ──┐
                              ├─▶ AuthenticationManager → DaoAuthenticationProvider
[REST 로그인 /api/.../login] ──┘         │
                                        ├─ loadUserByUsername() → assertNotLocked() (여기서 잠금 확인)
                                        └─ 인증 이벤트 발행 → SecurityAuditListener → onSuccess() / onFailure()
```

## 3. 프론트엔드(React) 보안  

- 브라우저에 도착한 모든 것은 이미 사용자에게 있음  

| 공격자가 브라우저에서 할 수 있는 일 | 그래서 |
| :--- | :--- |
| F12로 JS 소스를 전부 읽음 | 소스에 중요한 값을 둘 수 없음 |
| Burp로 요청을 가로채 바꾸거나 다시 보냄 | 최종 검사는 반드시 서버가 수행 |
| sessionStorage·localStorage·쿠키 값을 읽고 바꿈 | 브라우저에 저장한 값을 믿을 수 없음 |

### 3-1. 위변조된 토큰 거부  

- sessionStorage의 accessToken을 직접 조작해도 서버의 `JwtAuthenticationFilter`가 서명 검증에서 걸러 즉시 401 반환  

- JWT payload는 암호화가 아니라 Base64 인코딩 → 누구나 읽고 바꿀 수 있지만, 서명 키가 없으면 맞는 서명을 만들 수 없음  

- 서버에서 401을 받은 프론트엔드는 401이 변조인지 단순 만료인지 구분이 불가하고, refresh 절차를 시도할 뿐 → 변조 토큰은 서버가 이미 거부한 것이고, 프론트는 만료와 같은 흐름으로 전달

| 방어 | 내용 |
| :--- | :--- |
| 중복 갱신 방지 | 동시에 여러 401이 와도 `/refresh` 호출은 1회로 묶음 (두 번 나가면 재사용 탐지로 세션 전체 종료되므로) |
| 무한 재시도 방지 | 재시도는 1회만(`_retried`), `/refresh` 자체의 401은 갱신 대상에서 제외 |
| 갱신 실패 시 | 두 토큰 모두 즉시 폐기 → 로그인 화면으로 이동 |

### 3-2. 다른 Student 정보 수정 차단  

- 수정 라우트(`/students/:id/edit`)를 프론트에서 막지 않음 → 본인 것인지의 여부는 서버만 알기 때문  

- URL의 id를 바꿔 다른 학생 수정 화면에 들어가도 서버가 매 요청마다 소유권(`isOwner`)을 재검증해 403 반환 → 프론트는 서버 메시지를 보여주고 목록으로 돌려보냄  

| 구분 | 프론트엔드 | 서버 |
| :--- | :--- | :--- |
| 역할 | 권한 없는 화면·버튼을 숨김 | 실제로 막음 |
| 우회 | 개발자 도구로 조건 조작 가능 | 매 요청 토큰으로 다시 판정 → 우회 불가능 |

### 3-3. 토큰 저장 위치  

| 저장 위치 | 탭 닫기 | XSS 노출 시 |
| :--- | :--- | :--- |
| 메모리(변수/상태) | 사라짐 | 실행 중에만 노출 (가장 짧음) |
| sessionStorage | 사라짐 | 탭이 열린 동안 노출 |
| localStorage | 유지 | 영구 노출 |
| HttpOnly + Secure 쿠키 | 설정에 따름 | JS로 읽을 수 없음 (대신 CSRF 대비 필요) |

## 4. WSL과 Docker  

### 4-1. WSL (Windows Subsystem for Linux)  

- Windows 안에서 별도 가상머신 설정 없이 리눅스 환경을 실행할 수 있게 해주는 기능  

- WSL2는 실제 리눅스 커널을 경량 가상머신으로 실행 → 리눅스와의 호환성이 높음  

- Docker는 원래 리눅스 커널 기능을 기반으로 동작 → Windows에서 Docker Desktop을 쓰려면 WSL2가 필요  

### 4-2. Docker  

- 애플리케이션과 실행 환경(라이브러리, 설정 등)을 하나로 묶어 어디서든 똑같이 실행할 수 있게 해주는 컨테이너 플랫폼  

| 용어 | 뜻 |
| :--- | :--- |
| 이미지 (Image) | 실행에 필요한 모든 것을 담은 읽기 전용 템플릿 (클래스에 비유) |
| 컨테이너 (Container) | 이미지를 실행한 인스턴스 (객체에 비유) |
| Dockerfile | 이미지를 만드는 방법을 적은 설계도 |
| 레지스트리 (Registry) | 이미지를 저장·공유하는 저장소 |

| 구분 | 가상머신 (VM) | 컨테이너 |
| :--- | :--- | :--- |
| 구조 | 게스트 OS 전체를 포함 | 호스트 OS 커널을 공유 |
| 크기·속도 | 무겁고 부팅이 느림 | 가볍고 수 초 안에 실행 |
| 격리 수준 | 강함 | 프로세스 수준 격리 |
