## 1. 환경 변수로 컨테이너 설정하기  

- Docker 공식 이미지는 설정값을 환경 변수로 받도록 만들어져 있음 → 이미지를 수정하지 않고, 실행할 때 값만 바꿔서 재사용  

### 1-1. 환경 변수 전달 방법  

| 방법 | 특징 |
| :--- | :--- |
| `-e KEY=VALUE` | 값을 하나씩 명령어에 직접 전달 |
| `--env-file .env` | 파일에 모아둔 값을 한 번에 전달 |

- 비밀번호 등의 민감 정보들은 명령어에 직접 쓰면 셸 히스토리 등에 그대로 남음 → `.env` 파일로 분리  

### 1-2. 초기화는 처음 한 번만  

- DB 이미지는 데이터 저장 경로(볼륨)가 비어 있을 때만 초기화 진행  

```
1. 관리자 비밀번호 설정
2. 사용자 DB 생성
3. 사용자 계정 생성 + 권한 부여
4. /docker-entrypoint-initdb.d/ 의 .sql 파일 실행 (추가 초기화 작업)
```

- 이미 데이터가 있는 볼륨으로 시작하면 전부 건너뜀 → 환경 변수를 바꿔도 반영되지 않으므로 볼륨을 지우고 다시 시작해야 함

## 2. Dockerfile 작성 이유  

- 우리가 만든 App의 실행 환경을 Docker Image로 만들려면 (`docker build`) Dockerfile이 필요  

- 예를 들어, MariaDB처럼 공식 이미지가 있는 것은 그대로 쓰고, 직접 만든 Spring Boot 앱은 Dockerfile로 이미지를 만듦  

| 구분 | 이미지 출처 | Dockerfile |
| :--- | :--- | :--- |
| MariaDB | Docker Hub 공식 이미지 (`mariadb:10.11.18`) | 필요 없음 |
| Spring Boot 앱 | 직접 빌드 (`boot-mariadb-app`) | 필요 |

- Dockerfile에는 비밀번호를 직접 작성하지 않음 → 실행할 때 환경 변수로 전달  

```properties
# application.properties
# ${이름:기본값} → 환경 변수가 있으면 그 값, 없으면 기본값
spring.datasource.url=jdbc:mariadb://${DB_HOST:localhost}:${DB_PORT:3306}/${MARIADB_DATABASE:boot_db}
```

## 3. Docker Network  

- Docker에는 컨테이너 간에 통신을 편하게 하기 위해서 Network를 구성할 수 있음 

### 3-1. 컨테이너 안의 localhost  

- 컨테이너는 각자 전용 네트워크 공간(인터페이스, IP, localhost)을 가짐  

- 컨테이너 안에서 `localhost`는 그 컨테이너 자기 자신 → 앱 컨테이너에서 `localhost:3306`으로 접속하면 앱 컨테이너 안에서 DB를 찾다가 실패 -> DB 컨테이너와 연결 필요

### 3-2. 컨테이너 이름이 곧 주소  

- `docker network create` → 가상 네트워크 생성, 연결된 컨테이너는 그 대역의 IP를 하나씩 받음

- IP는 컨테이너를 다시 만들면 바뀔 수 있음 → 사용자 정의 네트워크는 내장 DNS가 컨테이너 이름을 현재 IP로 바꿔줌  

- 기본 `bridge` 네트워크는 이름으로 찾는 기능이 없음 → 네트워크를 직접 만드는 이유  

```bash
# mariadb, boot-app 2개의 주소 존재
docker network create boot-net
docker run -d --name mariadb  --network boot-net ... mariadb:10.11.18
docker run -d --name boot-app --network boot-net ... boot-mariadb-app
```

### 3-3. -p 포트 연결과 127.0.0.1  

- `-p 내PC포트:컨테이너포트`는 Docker 컨테이너 바깥(내 PC)에서 들어오는 요청을 컨테이너로 전달하는 설정  

- 로컬 → app → db로 이어진 구조가 아니라, 컨테이너마다 입구가 따로 존재

```
① 내PC:8092 ──(-p)──▶ app:8080 -> -p 8092:8080
② app(직접) ──▶ db:3306 -> 같은 네트워크 안의 통신이라 -p가 필요 없음
③ 내PC:3307 ──(-p)──▶ db:3306 -> -p 3307:3306
```

- `-p 3306:3306`은 내 PC의 모든 주소(`0.0.0.0`)에서 포트를 열어 같은 와이파이의 다른 PC도 접근 가능  

- `-p 127.0.0.1:3306:3306`은 내 PC의 localhost에서만 열림 → 내 PC 안의 프로그램만 접속 가능

## 4. Docker Volume  

- 컨테이너 내부 저장 공간은 컨테이너와 수명이 같음 → 컨테이너를 지우면 데이터도 사라짐  

- DB 컨테이너가 종료되더라도 DB의 데이터를 계속 유지해야 하기 때문에 volume이 필요  

```bash
-v mariadb-data:/var/lib/mysql
#  볼륨 이름  : 컨테이너 안 DB 데이터 저장 경로
```

| 볼륨 없음 | 볼륨 있음 |
| :--- | :--- |
| `docker rm -f mariadb` → DB, 테이블, 데이터 전부 삭제 | 컨테이너를 지워도 볼륨에 데이터가 남음 |
| 새로 실행하면 빈 DB | 같은 볼륨으로 다시 실행하면 이전 데이터 그대로 |

- 컨테이너(실행 환경)와 데이터의 수명을 분리하는 것 → 이미지를 업데이트해서 컨테이너를 새로 만들어도 데이터는 유지

## 5. Docker Compose  

- 단일 서버에서 여러 개의 컨테이너를 하나의 서비스로 정의하여 묶음으로 관리할 수 있게 해주는 도구  

- 각 컨테이너의 이미지, 환경 변수, 포트 포워딩, 볼륨 마운트, 네트워크 설정 등을 하나의 YAML 파일(`compose.yaml` / `docker-compose.yml`)에 문서화 및 관리  

### 5-1. 전용 네트워크 자동 생성  

- `docker compose up` 시 프로젝트 전용 네트워크를 자동으로 만들고 모든 서비스를 연결  

- 서비스 이름이 곧 접속 주소 → 앱은 `DB_HOST: mariadb`만 알면 됨 

- `docker compose down`은 컨테이너·네트워크만 삭제, 볼륨은 남음 (`-v`를 붙여야 볼륨까지 삭제)  

### 5-2. 의존성 및 실행 순서 관리

- 앱은 DB가 준비된 후에 시작되어야 함 → depends_on이 없으면 DB가 준비됐는지 직접 확인한 뒤 앱을 실행해야 함

```yaml
app:
  depends_on:
    mariadb:
      condition: service_healthy
```

| 쓰는 방법 | 앱이 시작되는 시점 |
| :--- | :--- |
| `depends_on: [mariadb]` | MariaDB 컨테이너가 시작되자마자 (DB 준비 전일 수 있음) |
| `condition: service_healthy` | MariaDB의 healthcheck가 통과한 뒤 |

- `service_healthy`를 쓰려면 DB 쪽에 `healthcheck:`가 반드시 있어야 함  

### 5-3. env_file vs 변수 치환  

```yaml
mariadb:
  env_file: .env                           # ① 파일 전체를 전달
app:
  environment:
    MARIADB_PASSWORD: ${MARIADB_PASSWORD}  # ② 필요한 값만 치환해서 전달
```

- MariaDB는 root 비밀번호까지 필요해서 전체 전달, 앱에는 필요한 값만 전달 → 앱 컨테이너에 root 비밀번호가 들어가지 않음 (비밀 값 노출 범위 축소)

## 6. Flyway  

- DB 스키마를 버전이 붙은 SQL 파일로 관리하는 DB 마이그레이션 도구  

| 역할 | 내용 |
| :--- | :--- |
| 스키마 버전 관리 | 테이블 변경 내역을 `V1__...sql`, `V2__...sql` 파일로 기록 → Git으로 관리 |
| 자동 스키마 마이그레이션 | 앱 시작 시 아직 적용 안 된 버전만 순서대로 실행 |
| 히스토리 추적 | `flyway_schema_history` 테이블에 적용 기록 저장 |
| ddl-auto 문제점 해결 | JPA가 자동으로 바꾸던 스키마를 명시적인 SQL로 관리 |

### 6-1. ddl-auto의 문제점  

| `ddl-auto=update`의 한계 | Flyway |
| :--- | :--- |
| 어떤 SQL이 실행됐는지 기록이 남지 않음 | 모든 변경이 SQL 파일로 남음 |
| 컬럼 이름 변경·삭제·데이터 이동 불가 | 원하는 SQL을 직접 작성 |
| 개발 DB와 운영 DB 구조가 달라지기 쉬움 | 어느 DB든 같은 파일을 같은 순서로 적용 |
| 초기 데이터를 넣을 방법이 없음 | `INSERT`도 마이그레이션으로 관리 |

| ddl-auto 값 | 동작 |
| :--- | :--- |
| `create` / `create-drop` | 테이블을 지우고 새로 만듦 (DROP 권한 필요) |
| `update` | 없는 테이블·컬럼만 추가 |
| `validate` | 아무것도 바꾸지 않고 Entity와 테이블이 맞는지 검사만 수행 |

- Flyway와 함께 쓸 때는 `validate` → 테이블은 Flyway가 만들고, JPA는 검사만 하는 안전장치 역할로 동작 

### 6-2. 동작 순서  

```
앱 시작
  ├─ 1. Flyway 실행
  │     ├─ flyway_schema_history 테이블이 없으면 생성
  │     ├─ 이미 적용된 파일의 체크섬이 바뀌었는지 검사 (바뀌었으면 시작 중단)
  │     └─ 아직 적용 안 된 버전만 순서대로 실행 (V1 → V2 → ...)
  ├─ 2. JPA (ddl-auto=validate) → Entity와 테이블 일치 여부 검사
  └─ 3. 웹 서버 시작
```

- Flyway가 JPA보다 먼저 실행 → JPA가 validate로 검사할 때는 테이블이 이미 준비되어 있음  

### 6-3. 파일 이름 규칙  

```
V1__create_memo_table.sql
│ │          └─ 설명 (밑줄은 공백으로 기록됨)
│ └─ 밑줄 2개 (1개면 인식 안 됨)
└─ 버전 (숫자 순서대로 실행)
```

- 위치: `src/main/resources/db/migration/`  

### 6-4. 지켜야 할 규칙  

| 규칙 | 어기면 |
| :--- | :--- |
| 이미 적용된 파일은 절대 수정하지 않음 | `Migration checksum mismatch` → 앱 시작 실패 |
| 변경은 항상 새 버전 파일로 추가 (V3, V4...) | - |
| Entity를 바꾸면 같은 내용의 마이그레이션도 추가 | `validate`가 `missing column` 오류로 시작 중단 |
