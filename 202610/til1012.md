## 1. RAG (Retrieval-Augmented Generation)  

- LLM이 답하기 전에 관련 문서를 검색해서 프롬프트에 함께 넣어 주는 방식  

    | LLM의 한계 | RAG의 해결 방식 |
    | :--- | :--- |
    | 학습 시점 이후의 정보를 모름 | 최신 문서를 검색해 컨텍스트로 전달 |
    | 비공개 문서(사내 규정 등)를 모름 | 문서를 벡터로 저장해 두고 질문과 관련된 부분만 전달 |

- 모르는 내용을 지어내는 **할루시네이션**을 줄이고, 답변의 **출처**를 제시할 수 있음  

### 1-1. 파이프라인  

```
[준비 - 문서당 1회]   Load → Split → Embed → Store
[질문마다]     Retrieve → (Augment) → Generate
```

| 단계 | 하는 일 | 구성 요소 |
| :--- | :--- | :--- |
| Load | 파일을 `Document` 리스트로 읽음 | Document Loader |
| Split | 긴 문서를 청크로 분할 | Text Splitter |
| Embed | 청크를 벡터로 변환 | Embedding 모델 |
| Store | 벡터와 원문을 저장 | Vector Store |
| Retrieve | 질문과 가까운 청크 검색 | Retriever |
| Generate | 검색 결과 + 질문으로 답변 생성 | Prompt + LLM |

---

## 2. Document Loader  

- 파일을 **`Document` 객체의 리스트**로 변환  
- `Document`는 `page_content`(본문) + `metadata`(정보)로 구성    

| 로더 | 대상 | `Document` 1개의 단위 | `metadata`에 자동 기록되는 키 |
| :--- | :--- | :--- | :--- |
| `TextLoader` | txt, md | 파일 전체 | `source` |
| `PyPDFLoader` | pdf | 페이지 | `source`, `page`(0부터), `page_label` |
| `CSVLoader` | csv | 행 | `source`, `row` |
| `Docx2txtLoader` | docx | 파일 전체 | `source` |

```python
from langchain_community.document_loaders import PyPDFLoader

documents = PyPDFLoader("../data/tutorial-korean.pdf").load()   # list[Document] 형태
print(len(documents), documents[0].metadata)
# {'source': '../data/tutorial-korean.pdf', 'page': 0, 'page_label': '1', ...}
```

- `metadata`: 본문이 어디에서 왔는지를 담은 dict → 로더가 자동으로 채움  

    | 키 | 값 |
    | :--- | :--- |
    | `source` | 파일 경로 |
    | `page` | PDF 페이지 번호 (0부터 시작) |
    | `page_label` | 문서에 표시된 페이지 번호 (1부터 시작) |
    | `row` | CSV 행 번호 (0부터 시작) |

- `load()`의 결과는 파일이 하나여도 **리스트** → 본문은 `documents[0].page_content`  

- `PyPDFLoader`는 텍스트가 들어 있는 PDF만 읽음 → 스캔 이미지 PDF는 OCR 필요  

- `metadata`는 분할 후에도 청크에 그대로 남음 → 답변의 출처(파일, 페이지) 표시에 사용

## 3. Text Splitter  

- 긴 `Document`를 검색하기 좋은 크기의 조각(**청크**)으로 나누는 도구 → 결과도 `Document` 리스트  

| 분할기 | 나누는 기준 |
| :--- | :--- |
| `CharacterTextSplitter` | 구분자 **하나**(기본 `"\n\n"`) → 구분자가 없는 긴 문단은 `chunk_size`를 넘을 수 있음 |
| `RecursiveCharacterTextSplitter` | 구분자 **목록**을 큰 단위부터 순서대로 시도 → `chunk_size`를 지키면서 문맥이 덜 끊김 |

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,                            # 청크 최대 길이
    chunk_overlap=200,                          # 이웃 청크가 겹치는 길이
    separators=["\n\n", "\n", ".", " ", ""],    # 문단 → 줄 → 문장 → 단어 → 글자
)
chunks = splitter.split_documents(documents) 
```

- `chunk_overlap`: 문장이 청크 경계에서 잘려 검색에서 빠지는 것을 방지 → 보통 `chunk_size`의 10~20%  

- `separators`는 **앞에 둔 것부터** 시도 → 문서에 반복되는 구조(조문의 `"\n제"`, 사례 구분 제목 등)를 맨 앞에 두면 그 경계에서 먼저 나뉨  

- `split_documents()`는 `Document` 리스트를 받음

## 4. Embedding  

- 텍스트를 **벡터**로 변환하는 것 → 의미가 비슷한 문장은 벡터가 서로 가까움  

    - 질문과 청크를 모두 벡터로 바꾸면 **거리**로 관련도를 비교할 수 있음 → 단어가 달라도 뜻이 같으면 검색됨  

```python
from langchain_openai import OpenAIEmbeddings
from langchain_upstage import UpstageEmbeddings
from langchain_ollama import OllamaEmbeddings

embeddings = UpstageEmbeddings(model="solar-embedding-1-large")
# embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
# embeddings = OllamaEmbeddings(model="bge-m3")
```

- 클래스만 바꾸면 나머지 코드는 그대로 → 모두 같은 `Embeddings` 인터페이스  

- `embed_query()`는 질문 1개, `embed_documents()`는 여러 문서를 변환  

- 인덱스를 만들 때와 검색할 때 **같은 임베딩 모델**을 써야 함 → 바꾸면 인덱스를 다시 생성

## 5. Vector Store  

- 청크의 **벡터와 원문을 함께 저장**해 두고, 질문 벡터와 가까운 벡터를 찾아 주는 데이터베이스  

    - Vector Store는 벡터가 **가까운** 청크를 찾음  

| 저장되는 것 | 용도 |
| :--- | :--- |
| 벡터 | 질문 벡터와의 거리 계산 (검색용) |
| `page_content`, `metadata` | 검색된 벡터에 해당하는 원문과 출처 (반환용) |

```
[저장]  청크 → 임베딩 모델 → 벡터 → 인덱스에 추가
[검색]  질문 → 같은 임베딩 모델 → 질문 벡터 → 가까운 벡터 k개 → 해당 청크 반환
```

- 벡터만으로는 원문을 알 수 없고, 원문을 같이 저장해 두었다가 벡터로 찾고 원문을 돌려줌

```python
from langchain_community.vectorstores import FAISS

vectorstore = FAISS.from_documents(chunks, embeddings)   # 청크 임베딩 + 저장
vectorstore.save_local("../db/faiss_index")              # 파일로 저장

vectorstore = FAISS.load_local("../db/faiss_index", embeddings, allow_dangerous_deserialization=True)

docs = vectorstore.similarity_search("질문", k=3)        # 가까운 청크 3개
```

- 임베딩 모델을 함께 넘기는 이유: 저장할 때는 청크를, 검색할 때는 질문을 벡터로 바꿔야 하기 때문  

- `from_documents()` 안에서 임베딩 API가 호출됨 → 저장해 두고 `load_local()`로 재사용하면 시간·비용 절약

## 6. Retriever  

- 질문을 받아 관련 `Document` 리스트를 돌려주는 검색기

    - Vector Store는 저장소, Retriever는 그 저장소에 검색 방식과 개수를 정해 둔 검색 창구  

    - Runnable이라 `invoke()`로 호출하고 `|`로 체인에 연결할 수 있음 
    - Vector Store는 체인에 바로 연결할 수 없음   

```python
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 5},
)
docs = retriever.invoke("질문")   # list[Document]
```

| `search_type` | 고르는 기준 | `search_kwargs` |
| :--- | :--- | :--- |
| `similarity` | 질문과 가까운 순서대로 `k`개 | `k` |
| `mmr` | 질문과 가까우면서 서로 내용이 겹치지 않는 `k`개 | `k`, `fetch_k` |

- MMR(Maximum Marginal Relevance): 후보 `fetch_k`개를 먼저 가져온 뒤, 이미 고른 문서와 덜 비슷한 것을 하나씩 추가해 `k`개 선택 → 비슷한 청크만 반복해서 뽑히는 것을 방지

## 7. 답변 생성  

- 검색된 청크를 프롬프트에 끼워 넣고(Augment), LLM이 그 내용을 근거로 답변을 만드는(Generate) 단계  

    - LLM은 Vector Store를 직접 보지 않고 프롬프트의 `{context}`에 들어온 텍스트만 읽음  

- 프롬프트에 검색 결과가 들어갈 `{context}`와 질문이 들어갈 `{question}` 자리를 둠  

### 7-1. LCEL 체인  

- 검색 → 프롬프트 → LLM → 파서를 `|`로 이어 질문 하나로 답변까지 나오게 만듦

```python
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
answer = rag_chain.invoke("질문") 
```

- 질문 하나가 두 갈래로 나뉨 → `retriever | format_docs`는 검색 결과를 문자열로 합치고, `RunnablePassthrough()`는 질문을 그대로 전달  

- `invoke()`에 질문 문자열을 넘기면 그 문자열이 retriever와 `RunnablePassthrough()` 양쪽으로 들어감

## 8. LangGraph  

- LLM 호출 흐름을 **노드(작업)와 엣지(순서)의 그래프**로 구성하는 라이브러리  

    - LCEL 체인은 앞 단계의 출력이 곧 다음 단계의 입력, LangGraph는 모든 노드가 **하나의 State를 공유**하며 읽고 씀  

| 용어 | 뜻 |
| :--- | :--- |
| State | 그래프 전체가 공유하는 데이터 → `TypedDict`로 필드를 미리 정의 |
| Node | State를 받아 **바뀐 필드만** dict로 돌려주는 함수 → 돌려준 값은 State에 병합됨 |
| Edge | 노드의 실행 순서 → `START`에서 첫 노드로 연결 |

```python
class State(TypedDict):
    question: str
    thinking: str
    answer: str

def think(state: State):        
    return {"thinking": ...}

def generate(state: State):    
    return {"answer": ...}

graph = StateGraph(State).add_sequence([think, generate]).add_edge(START, "think").compile()
result = graph.invoke({"question": "질문"})
```

- 추론은 `deepseek-r1`, 한국어 답변은 `qwen2.5` 처럼 노드별로 다른 모델에 역할을 나눠 맡길 수 있음

## 9. Gradio  

- 파이썬 함수에 **웹 UI**를 붙여 주는 라이브러리
- 함수 + 입력/출력 컴포넌트 + `launch()`로 구성  

| 방식 | 특징 |
| :--- | :--- |
| `gr.Interface` | 함수 하나와 입력·출력만 지정하면 화면을 자동으로 만들어 줌 |
| `gr.Blocks` | 컴포넌트 배치와 버튼 동작을 직접 구성 |

- Flag: `gr.Interface` 화면의 버튼 → 누른 시점의 입력과 출력을 CSV로 저장하여 잘못된 답변을 나중에 검토할 수 있음
