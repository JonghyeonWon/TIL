## 1. 프롬프트 템플릿  

| 템플릿 | 만드는 것 | 사용처 |
| :--- | :--- | :--- |
| `PromptTemplate` | 문자열 프롬프트 하나 | 단순 지시 |
| `ChatPromptTemplate` | `(역할, 내용)` 메시지 목록 | `system` / `user` 역할 구분 |
| `SystemMessagePromptTemplate` 등 | 메시지 하나짜리 템플릿 객체 | 조건에 따라 메시지를 바꿔 끼울 때 |
| `FewShotChatMessagePromptTemplate` | 예시 `human → ai` 메시지 묶음 | 출력 형식을 예시로 고정 |

- 템플릿끼리, 또는 템플릿과 문자열을 `+`로 이어 붙일 수 있음  

- Few-shot: 예시 데이터(`examples`)와 형식(`example_prompt`)을 분리  

    - 예시 0개는 Zero-shot, 1개는 One-shot, 여러 개는 Few-shot  

### 1-1. Partial Prompt  

```python
prompt = PromptTemplate(
    template="{season}에 일어나는 대표적인 지구과학 현상은 {phenomenon}이 맞나요?",
    input_variables=["phenomenon"],                     # invoke() 때 받는 값
    partial_variables={"season": get_current_season},   # 미리 채워 두는 값
)
```

- Partial Prompt: 변수 중 일부를 **미리 채워 둔** 프롬프트 → 호출하는 쪽은 남은 변수만 넘김  

- 값 대신 **함수 자체**를 넘기면 `format()`을 부를 때마다 실행됨 → 날짜, API 결과처럼 매번 달라지는 값에 사용  

- 이미 만든 프롬프트에는 `.partial(변수=값)`으로 채움

## 2. Output Parser  

### 2-1. 공통 패턴  

```python
parser = CommaSeparatedListOutputParser()

prompt = PromptTemplate(
    template="List five {subject}.\n{format_instructions}",
    input_variables=["subject"],
    partial_variables={"format_instructions": parser.get_format_instructions()},
)

chain = prompt | llm | parser
result = chain.invoke({"subject": "AI 관련 기술"})
```

- 파서가 하는 일 2가지  

    - `get_format_instructions()`: "이런 형식으로 답하라"는 **지침 문자열** → 프롬프트에 넣지 않으면 모델은 형식을 모름  

    - `parse()`: 응답 문자열을 파이썬 값으로 변환 → 형식이 다르면 `OutputParserException`  

- 어떤 파서든 순서는 같음: 파서 생성 → 프롬프트에 지침을 `partial`로 주입 → 체인 마지막에 파서 붙임  

### 2-2. 종류  

| 파서 | 결과 타입 | 형식 정의 |
| :--- | :--- | :--- |
| `StrOutputParser` | `str` | 없음 (`AIMessage`의 본문만 꺼냄) |
| `CommaSeparatedListOutputParser` | `list[str]` | 없음 |
| `JsonOutputParser` | `dict` | 프롬프트에서 키 이름 지정 (검증 없음) |
| `PydanticOutputParser` | Pydantic 객체 | `BaseModel` + `Field` |
| `EnumOutputParser` | `Enum` 멤버 | `Enum` 클래스 |
| `StructuredOutputParser` | `dict` | `ResponseSchema` 목록 |
| `OutputFixingParser` | 감싼 파서와 같음 | 다른 파서를 감쌈 |

### 2-3. `EnumOutputParser`  

```python
class Sentiment(Enum):
    POSITIVE = "긍정"
    NEGATIVE = "부정"
    NEUTRAL = "중립"

parser = EnumOutputParser(enum=Sentiment)

prompt = ChatPromptTemplate.from_messages([
    ("system", "리뷰를 읽고 감성을 분류하세요. 설명 없이 값만 답하세요.\n{format_instructions}"),
    ("user", "리뷰: {review}"),
]).partial(format_instructions=parser.get_format_instructions())

result = (prompt | llm | parser).invoke({"review": "배송도 빠르고 품질도 좋아요."})
```

- 답변을 **미리 정한 값 중 하나**로 제한  

- 결과는 문자열이 아니라 Enum 멤버 → 문자열은 `result.value`로 표현  

### 2-4. `OutputFixingParser`  

```python
fixing_parser = OutputFixingParser.from_llm(llm=llm, parser=parser, max_retries=1)
chain = prompt | llm | fixing_parser
```

- 파싱에 실패하면 **잘못된 응답 + 오류 내용 + 형식 지침**을 LLM에 다시 보내 고친 응답으로 재파싱  

- 실패할 때만 LLM이 추가로 호출됨 → 비용·응답 시간 증가  

- 고친 뒤에도 틀리면 다시 예외 → `try / except OutputParserException`은 여전히 필요  

### 2-5. `PydanticOutputParser`  

```python
class ReviewAnalysis(BaseModel):
    """제품 리뷰 분석 결과"""
    rating: float = Field(ge=0, le=5, description="5점 만점 예상 평점")
    pros: list[str] = Field(description="장점 3가지")
    summary: str = Field(description="리뷰 한 문장 요약")

parser = PydanticOutputParser(pydantic_object=ReviewAnalysis)

prompt = ChatPromptTemplate.from_messages([
    ("system", "당신은 제품 리뷰 분석 전문가입니다. 다음 형식을 정확히 따르세요:\n{format_instructions}"),
    ("user", "리뷰 내용: {review}"),
]).partial(format_instructions=parser.get_format_instructions())

output = (prompt | llm | parser).invoke({"review": review})
print(output.summary)
```

- `get_format_instructions()`가 클래스를 **JSON 스키마**로 바꿔 지침에 넣음 → 모델은 이 스키마를 보고 JSON으로 답함  

    ```
    "rating": {"description": "5점 만점 예상 평점", "minimum": 0, "maximum": 5, "type": "number"}
    "pros":   {"description": "장점 3가지", "items": {"type": "string"}, "type": "array"}
    ```

    - 타입 힌트(`float`, `list[str]`)는 `type`으로, `ge` / `le`는 `minimum` / `maximum`으로, `description`은 그대로 들어감  

    - 필드 이름과 타입만으로는 **무엇을 넣을지** 알 수 없음 → 그 뜻을 알려 주는 것이 `description`  

- 응답을 **타입까지 검증**  

    | 모델 응답 | 결과 |
    | :--- | :--- |
    | `"rating": "4.5"` | `float` 4.5로 변환 |
    | `"rating": "높음"` | 숫자로 바꿀 수 없음 → 예외 |
    | `"rating": 7` | `le=5` 범위 초과 → 예외 |
    | `"pros": "배터리"` | 리스트가 아님 → 예외 |

### 2-6. `StructuredOutputParser`  

```python
response_schemas = [
    ResponseSchema(name="title", description="추천 영화 또는 드라마 제목"),
    ResponseSchema(name="genre", description="장르"),
    ResponseSchema(name="reason", description="추천 이유 (한 문장)"),
]
parser = StructuredOutputParser.from_response_schemas(response_schemas)

prompt = ChatPromptTemplate.from_messages([
    ("system", "당신은 영화/드라마 추천 전문가입니다. 반드시 아래 형식을 지키세요.\n{format_instructions}"),
    ("user", "{question}"),
]).partial(format_instructions=parser.get_format_instructions())

response = (prompt | llm | parser).invoke({"question": "가족과 볼 영화를 추천해 주세요."})
print(response["title"])
```

- `name`이 결과 dict의 **키**, `description`이 모델에게 주는 설명  

- `type`(기본 `"string"`)은 지침에 표시만 되고 **검증하지 않음**  

- 정의한 키가 응답에 빠지면 예외  

### 2-7. Pydantic vs Structured  

| 구분 | `PydanticOutputParser` | `StructuredOutputParser` |
| :--- | :--- | :--- |
| 형식 정의 | `BaseModel` 클래스 | `ResponseSchema` 목록 |
| 결과 | Pydantic 객체 (`output.summary`) | `dict` (`response["title"]`) |
| 검증 | 타입·범위까지 | 키가 있는지만 |

- 둘 다 모델에게 JSON으로 답하게 하는 것은 같고, **받은 값을 얼마나 믿을 수 있는지**가 다름  

- 숫자·리스트처럼 타입이 중요하면 Pydantic, 문자열 몇 개만 간단히 받으면 Structured 사용

## 3. Model Parameter  

| 파라미터 | 조절하는 것 |
| :--- | :--- |
| `temperature` | 다음 토큰을 고르는 무작위성 → 높을수록 다양한 답 |
| `top_p` | 후보로 삼을 토큰의 범위 지정 → 높을수록 확률이 낮은 토큰까지 후보에 포함 |
| `presence_penalty` | **이미 나온** 토큰에 페널티 부과 → 높을수록 새 주제로 넘어감 |
| `frequency_penalty` | **나온 횟수**에 비례한 페널티 부과 → 높을수록 같은 단어 반복 억제 |
| `max_tokens` | 응답 길이 상한 |
| `stop` | 이 문자열이 나오면 응답 중단 |

## 4. LLM 체인을 REST API로  

- 로컬에서만 돌리던 체인을 **HTTP 요청으로 호출**할 수 있게 서버에 올리는 것 → 화면(웹·앱)이 질문을 보내고 답변을 받을 수 있음  

    | 용어 | 뜻 |
    | :--- | :--- |
    | FastAPI | 파이썬으로 REST API 서버를 만드는 프레임워크 |
    | LangServe | 체인을 넘기면 FastAPI 엔드포인트를 **자동으로** 만들어 주는 도구 |
    | SSE (Server-Sent Events) | 서버가 응답을 한 번에 보내지 않고 **조금씩 이어서** 보내는 방식 |

### 4-1. 체인을 서빙하는 2가지 방법  

```python
# 방법 1) LangServe: 엔드포인트를 자동으로 생성
add_routes(app, chain, path="/chat")

# 방법 2) FastAPI: 엔드포인트를 직접 작성
@app.post("/chat")
async def chat(body: QuestionInput):
    result = await chain.ainvoke({"question": body.question})
    return {"answer": result.content}
```

- 둘 다 **같은 체인을 HTTP로 호출할 수 있게** 하는 방법 → 엔드포인트를 누가 만드느냐만 다름  

- LangServe도 FastAPI 앱 위에서 동작 → 방법 2의 코드를 대신 써 주는 것  

- LangServe는 빠르게 올릴 때, FastAPI 직접 작성은 요청·응답 형식을 원하는 대로 정할 때 사용  

### 4-2. SSE 스트리밍  

```python
async def event_generator():
    async for chunk in chain.astream({"question": body.question}):
        yield f"data: {chunk.content}\n\n"

return StreamingResponse(event_generator(), media_type="text/event-stream")
```

- **SSE(Server-Sent Events)**: 연결을 열어 둔 채 서버가 데이터를 여러 번 나눠 보냄 → 답변이 완성되기를 기다리지 않고 바로 보여줌  

- 체인의 `astream()`이 답변을 조각(chunk) 단위로 내주고, 서버는 조각마다 `data: 내용` + 빈 줄 형식으로 전송

## 5. LangSmith  

- LLM 애플리케이션의 실행 과정을 기록하고, 답변 품질을 평가하는 웹 서비스  

    - 체인은 결과만 돌려주므로 중간에 어떤 프롬프트가 들어갔고 어디서 오래 걸렸는지 알기 어려움 → LangSmith 사이트에서 단계별로 확인  

| 기능 | 하는 일 |
| :--- | :--- |
| 트레이싱 | 실행할 때마다 단계별 입력·출력, 토큰 수, 걸린 시간을 기록 |
| 평가 | 같은 질문 모음으로 모델을 돌려 보고 점수를 매겨 비교 |

### 5-1. 트레이싱  

```python
@traceable(name="Tagged_Chain", tags=["upstage", "demo"], metadata={"app_version": "v1"})
def ask_question(question: str):
    return (prompt | llm).invoke({"question": question}).content
```

- `.env`에 LangSmith 키(`LANGSMITH_API_KEY` 등)를 등록하면 LangChain 실행은 **자동으로 기록**됨  

- 직접 만든 함수는 `@traceable`을 붙여야 기록됨  

- `tags`(라벨)와 `metadata`(부가 정보)를 붙여 두면 사이트에서 원하는 실행만 **필터링**해서 찾을 수 있음  

### 5-2. 평가  

| 용어 | 뜻 |
| :--- | :--- |
| Dataset | 평가에 쓸 질문 모음 → LangSmith에 저장해 두고 재사용 |
| evaluator | 답변을 보고 점수를 매기는 함수 |

- 흐름: Dataset 생성 → evaluator 작성 → `evaluate()`로 모델마다 실행 → 사이트에서 점수 비교  

- 평가 기준은 직접 정함 → 예: 한국어로 답했는지, 300자 이내인지
