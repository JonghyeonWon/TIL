## 1. Logging Hardening

- 로그인 성공/실패, 401/403 등을 로그로 남겨 누가 무엇을 시도했는지 추적  

- 비밀번호·JWT·세션ID는 절대 로그에 남기지 않고, 이메일 같은 정보도 `us***@aa.com`처럼 마스킹  

### 1-1. 웹 보안 vs 메서드 보안  

| 구분 | 웹 보안 (Web Security) | 메서드 보안 (Method Security) |
| :--- | :--- | :--- |
| 설정 위치 | `securityConfig` | 컨트롤러/서비스 메서드의 `@PreAuthorize` |
| 검사 대상 | URL 규칙 (`/api/**`, `/actuator/**`) | `@PreAuthorize`에 적은 조건 충족 여부 (역할, 본인 여부 등) |
| 평가 시점 | DispatcherServlet 이전 (필터 체인) | DispatcherServlet 이후 (메서드 호출 시점) |
| 실패 처리 | `securityConfig` 내부 | `@RestControllerAdvice` |

- 같은 403이라도 어디서 막혔는지에 따라 처리하는 곳이 달라짐  

### 1-2. Advice만으로 부족한 이유  

```
클라이언트 요청
   │
   ▼
[1] 필터 체인 (DispatcherServlet 이전) → securityConfig 에서 처리
   ├─ 인증 실패 (토큰 없음/무효) → AuthenticationEntryPoint → 401
   ├─ 인가 실패 (URL 규칙 위반) → AccessDeniedHandler → 403
   │     ※ 여기서 응답이 끝나고, controller로 도달하지도 못함
   │
   ▼ 통과
[2] DispatcherServlet → controller → Advice 에서 처리
   └─ @PreAuthorize 실패 → DefaultExceptionAdvice → 403
```

- `@RestControllerAdvice`는 컨트롤러 계층에서 발생한 예외만 받음 → 필터 체인에서 끝난 요청은 Advice가 볼 수 없음  

- 예외 발생 지점에 따라 Advice / securityConfig 중 한쪽만 호출되므로 한쪽에만 로그를 두면 다른 경로의 401/403은 추적 불가능 → Advice에 추가로 securityConfig의 두 핸들러에서도 직접 로그를 남김

```java
// securityConfig의 chain 중 일부
.exceptionHandling(ex -> ex
        .authenticationEntryPoint(authenticationEntryPoint())   // 401
        .accessDeniedHandler(auditedAccessDeniedHandler()))     // 403
```

## 2. Advanced JWT  

- 1단계(secret 하드닝)에 이어, secret이 유출된 상황에서도 공격 범위와 피해 시간을 줄일 수 있는 방어 체계가 필요  

| 취약점 | 방어 |
| :--- | :--- |
| payload 노출 → PII 유출 | JWT Token의 subject를 email → uuid로 변경 |
| 로그아웃해도 탈취된 토큰이 만료시간까지 유효 | 짧은 Access time + 서버 DB에 저장하는 Refresh |
| DB 유출 시 refresh 원문 노출 | SHA-256 해시로 저장 |

### 2-1. subject를 uuid로 변경 

- PII(개인 식별 정보): 이름·email·전화번호처럼 개인을 알아볼 수 있는 정보 

- payload는 base64라 누구나 읽을 수 있으므로 넣으면 안 됨  

- secret이 유출되어도 uuid를 모르면 위조 불가 (uuid는 추측 불가하므로)

```java
// Before: subject = email (PII, 추측 가능)
jwtService.generateToken(userDetails.getUsername());
// After : subject = uuid (불투명, 어떤 API로도 노출 x)
jwtService.generateToken(userDetails.getUuid());
```

- JWT 필터도 `loadUserByUsername(email)` → `loadUserByUuid(uuid)`로 조회  

### 2-2. Access Token + Refresh Token  

- JWT는 stateless → 서버가 상태를 기억하지 않아 서명만 맞으면 만료 전까지 유효 

| 구분 | Access Token | Refresh Token |
| :--- | :--- | :--- |
| 형태 | JWT | 무작위 불투명 문자열 (JWT 아님) |
| 수명 | 짧게 (15분) | 길게 (14일) |
| 사용 | API 호출마다 `Authorization` 헤더 | access 만료 시 `/refresh` 호출할 때만 |
| 저장 | 서버에 저장 x | 서버 DB에 저장 → 조회·폐기·교체 가능 |

```
1. 로그인 → access(15분) + refresh(DB 저장) 발급

2. access 만료 → POST /refresh 요청 → 새 access + 새 refresh 발급, 기존 refresh는 폐기 (revoked=1)

3. 로그아웃 → POST /logout → 요청에 담긴 refresh와 일치하는 row를 DB에서 삭제
```

| 상황 | Refresh 없음 | Access 15분 + Refresh |
| :--- | :--- | :--- |
| 탈취 후 사용 가능 시간 | 만료까지 (60분) | 최대 15분 |
| 로그아웃 | 탈취된 토큰 여전히 유효 | refresh 폐기 → 다음 갱신부터 차단 |
| 탈취 토큰 재사용 | 구분 불가 | 폐기된 refresh 재사용 → 탐지 + 401 반환 |

### 2-3. 해시 저장 + 재사용 탐지  

- DB에는 원문 대신 해시값 `tokenHash`(SHA-256)만 저장, 원문은 응답으로만 전달 
- DB가 유출되어도 해시는 단방향이라 원문 복원 불가  

- 회전(refresh) 시 기존 토큰을 삭제하지 않고 `revoked=1`로 남겨 둠 → 폐기된 토큰이 다시 들어오면 누군가 훔쳐 쓰고 있다고 판단 가능  

```java
if (rt.isRevoked()) {
    log.warn("[AUDIT] refresh 토큰 재사용 감지 - userUuid={}", rt.getUserUuid());
    reuseGuard.revokeAll(rt.getUserUuid());   // 해당 사용자의 모든 refresh 삭제
    throw new BadCredentialsException("재사용이 감지되어 모든 세션이 종료되었습니다");
}
```

- 새 row를 추가하는 이유: 기존 row를 덮어쓰면 refresh 전에 어떤 토큰이 있었는지 사라져 재사용 탐지가 불가  

### 2-4. `@Transactional` 전파 속성  

- 전파: 트랜잭션이 이미 진행 중인 상태에서 다른 `@Transactional` 메서드를 호출할 때 어떻게 동작할지 정하는 속성  

| 속성 | 기존 트랜잭션 있음 | 기존 트랜잭션 없음 |
| :--- | :--- | :--- |
| `REQUIRED` (기본값) | 기존 트랜잭션에 참여 | 새로 시작 |
| `REQUIRES_NEW` | 새 트랜잭션 시작 | 새로 시작 |
| `MANDATORY` | 기존 트랜잭션에 참여 | 예외 발생 (반드시 트랜잭션 안에서 호출되어야 함) |

- `REQUIRED`: 하나로 묶여 같이 커밋/롤백 → 안쪽에서 예외가 나면 전체 롤백  

- `REQUIRES_NEW`: 독립 트랜잭션이라 바깥이 롤백돼도 안쪽은 이미 커밋된 상태 유지  

- `MANDATORY`: 상위 트랜잭션의 일부여야 하는 작업을 강제할 때 사용

## 3. XSS (Cross-Site Scripting)  

- 공격자가 넣은 문자열이 다른 사용자의 브라우저에서 HTML/스크립트로 해석·실행되는 취약점  

- SQL Injection은 입력이 DB 명령으로, XSS는 입력이 브라우저 명령(HTML/JS)으로 실행

| 유형 | 내용 |
| :--- | :--- |
| Stored (저장형) | 입력이 DB에 저장 → 그 데이터를 보는 모든 사용자에게 실행 (피해 범위 가장 넓음) |
| Reflected (반사형) | 입력이 그 요청의 응답에만 반사 → 피해자가 공격 링크를 클릭해야 함 |
| DOM-based | 서버를 거치지 않고 브라우저 JS가 `innerHTML` 등으로 직접 삽입 |

- 이스케이프(escape): 특별한 의미를 가진 문자를 다른 표기로 바꿔 명령이 아닌 글자로 취급되게 하는 처리

   - 이스케이프를 통해 `<script>`를 `&lt;script&gt;`로 바꿔 보내면 브라우저는 태그가 아닌 `<script>`라는 글자로 표시

- 핵심 원인은 출력 시점에 이스케이프하지 않는 것 → 출력할 때 `<`, `>`, `&`, `"`를 엔티티(`&lt;`, `&gt;`...)로 바꾸는 것이 근본 대응   

### 3-1. `th:text` vs `th:utext`  

```html
<td th:text="${user.name}"></td>    <!-- 안전: 자동 이스케이프 -->
<td th:utext="${user.name}"></td>   <!-- 취약: 그대로 HTML로 해석 -->
```

| 속성 | 이스케이프 | `<script>alert(1)</script>` 입력 시 |
| :--- | :--- | :--- |
| `th:text` (권장) | 자동 처리 | `&lt;script&gt;...` → 문자열로만 표시 |
| `th:utext` | 처리 안 함 | `<script>...` → 브라우저가 실행 |

### 3-2. CSP (Content-Security-Policy)  

- 서버가 HTTP 응답 헤더로 어느 출처의 리소스까지 실행·로드할지 선언하고, 브라우저가 그 규칙을 강제하는 보안 메커니즘  

- 출력 이스케이프가 1차 방어라면, CSP는 이스케이프를 빠뜨렸을 때의 2차 방어선  

```java
// SecurityConfig.formLoginFilterChain
.headers(headers -> headers
        // CSP 설정
        .contentSecurityPolicy(csp -> csp
                .policyDirectives(
                        "default-src 'self'; "
                        + "script-src 'self' https://cdn.jsdelivr.net; "
                        + "style-src 'self' https://cdn.jsdelivr.net; "
                        + "img-src 'self'; "
                        + "object-src 'none'; "
                        + "base-uri 'self'; "
                        + "frame-ancestors 'self'")))
```

| 지시어 | 의미 |
| :--- | :--- |
| `default-src 'self'` | 기본적으로 우리 서버의 리소스만 허용 |
| `script-src` / `style-src` | 스크립트·스타일은 우리 서버 + Bootstrap CDN만 허용 |
| `img-src 'self'` | 이미지는 우리 서버 것만 허용 |
| `object-src 'none'` | `<object>`, `<embed>` 같은 플러그인 사용 금지 |
| `base-uri 'self'` | 상대경로의 기준 주소를 바꾸지 못하게 함 |
| `frame-ancestors 'self'` | 다른 사이트가 우리 페이지를 iframe으로 넣지 못하게 함 |

- `script-src`에 `'unsafe-inline'`이 없으므로 HTML 안에 직접 쓴 스크립트는 실행 금지 → 공격자가 `<script>`를 심어도 브라우저가 실행하지 않음
