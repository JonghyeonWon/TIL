## 1. Docker Compose yml 구조  

- 여러 컨테이너의 실행 설정을 YAML 파일 하나에 선언해 두는 것  

- `docker compose up` 한 번으로 네트워크 생성 → 볼륨 생성 → 컨테이너 실행 순서까지 처리  

### 1-1. 최상위 키  

```yaml
name: boot-flyway     # 프로젝트 이름 → 컨테이너·네트워크·볼륨 이름 앞에 붙음 
services:             # 실행할 컨테이너 목록 (서비스 이름 = 접속 주소)
  mariadb: ...
  app: ...
volumes:              # 이름 있는 볼륨 선언 (실제 이름: boot-flyway_mariadb-data)
  mariadb-data:
# networks: 생략하면 boot-flyway_default 네트워크를 자동 생성해서 모든 서비스 연결
```

### 1-2. 서비스 안의 주요 키  

| 키 | 의미 | `docker run`으로 치면 |
| :--- | :--- | :--- |
| `image` | 사용할 이미지 | 마지막 인자 `mariadb:10.11.18` |
| `build` | 이 폴더의 Dockerfile로 이미지 빌드 | `docker build .` |
| `env_file` | 파일 전체를 환경 변수로 전달 | `--env-file .env` |
| `environment` | 필요한 값만 골라서 전달 | `-e KEY=VALUE` |
| `ports` | 호스트 포트 ↔ 컨테이너 포트 | `-p` |
| `volumes` | 볼륨 마운트 | `-v` |
| `healthcheck` | 상태 검사 명령 | `--health-cmd ...` |
| `depends_on` | 실행 순서 제어 | 직접 기다렸다가 실행 |
| `restart` | 종료 시 재시작 정책 | `--restart` |

## 2. GitHub Actions  

- GitHub 저장소에 내장된 CI/CD 자동화 도구 

- 이벤트(push, PR 등)가 일어나면 정해진 작업을 GitHub의 가상 머신에서 자동 실행  

- CI(continuous integration): 코드가 합쳐질 때마다 자동 빌드·테스트 

- CD(continuous deployment): 결과물을 배포 가능한 상태(이미지 등)로 만들거나 배포까지 자동화  

### 2-1. 특징  

- Runner: 워크플로를 실행하는 GitHub의 가상 머신

- 실행할 때마다 깨끗한 새 Runner에서 시작하고, 끝나면 사라짐 → 내 PC 환경에 의존하지 않는 일관된 빌드  

- 이전 실행의 파일이 남지 않음 → 의존성·빌드 레이어 재사용은 캐시(`cache: maven`, `type=gha`)로 해결  

- Marketplace의 Action을 조합하면 Docker 로그인·빌드·push 등을 몇 줄로 구성 가능  

- 실행 결과는 저장소의 Actions 탭에서 단계별 로그로 확인 가능  

### 2-2. Secrets  

- 비밀번호·토큰은 yml에 직접 쓰지 않고 Github 저장소의 `Settings > Secrets and variables > Actions`에 등록  

- `${{ secrets.DOCKER_USERNAME }}`처럼 사용, 로그에는 `***`로 가려짐  

- `DOCKER_PASSWORD`에는 비밀번호 대신 Access Token 권장 → 유출되면 토큰만 삭제하면 되고 권한 범위도 제한 가능

## 3. BackEnd(Spring Boot) Docker Build & Push  

### 3-1. 단계 흐름  

- Checkout: Runner에 저장소 코드를 내려받는 단계

  - Runner는 매번 빈 상태로 시작하므로, 이 단계가 없으면 `pom.xml`, `Dockerfile`, `src`가 없어 뒤 단계가 모두 실패

```
1. Checkout              actions/checkout@v4          저장소 코드 내려받기 

2. Set up JDK 17         actions/setup-java@v4        JDK 설치 + ~/.m2 캐시

3. Build with Maven      mvn -B clean package         빠른 컴파일 오류 확인
                         -Dmaven.test.skip=true       (Runner에는 DB가 없어 테스트 생략)
── 여기부터 push일 때만 ──
4. Set up Buildx         docker/setup-buildx-action   빌드 캐시를 쓰기 위한 빌더 준비

5. Login to Docker Hub   docker/login-action          secrets로 로그인

6. Build & push          docker/build-push-action     Dockerfile 빌드 → Docker Hub 업로드
```

- 실제 이미지 안의 JAR는 Dockerfile(멀티 스테이지)에서 다시 빌드됨 → 3번은 문제가 있는 경우에 빨리 실패하기 위한 확인 용도  

### 3-2. 빌드 캐시  

- Runner는 매번 새 머신이라 레이어 캐시가 남지 않음 → `cache-from: type=gha`(가져오기), `cache-to: type=gha,mode=max`(저장)로 GitHub 캐시를 사용해서 `pom.xml`이 그대로면 의존성 다운로드를 생략 가능

## 4. FrontEnd(React) Docker Build & Push  

### 4-1. 백엔드 워크플로와 차이점  

| 항목 | BackEnd | FrontEnd |
| :--- | :--- | :--- |
| 환경 준비 | `actions/setup-java` (JDK 17) | `actions/setup-node` (Node 22) |
| 빌드 확인 | `mvn -B clean package` | `npm ci && npm run build` |
| 이미지 저장소 | `아이디/boot-flyway-app` | `아이디/boot-flyway-web` |
| 이후 단계 | Buildx → Login → Build & Push | 동일 |

- `npm ci`: `package-lock.json`을 토대로 설치 

### 4-2. React 이미지 구조 (멀티 스테이지)  

```dockerfile
FROM node:22-alpine AS build        # 1단계: npm run build → /app/dist (정적 파일)

FROM nginx:1.27-alpine              # 2단계: nginx가 dist 제공
COPY nginx/default.conf.template /etc/nginx/templates/default.conf.template
COPY --from=build /app/dist /usr/share/nginx/html
ENV BACKEND_URL=http://app:8080
```

- React 빌드 결과는 HTML/JS/CSS 정적 파일 → 실행에는 Node가 필요 없고 웹 서버(nginx)만 있으면 됨 → 이미지에 Node가 빠져 용량 감소

## 5. 전체 흐름  

```
내 PC ──git push──▶ GitHub Actions 자동 실행──▶ Docker Hub에 반영 (app, web 이미지)
                                             │ docker compose pull
                                             ▼
EC2 ─────────────────────────────────────────────────────────────
│ 인터넷 ──80──▶ web(nginx) ──/api──▶ app:8080 ──▶ mariadb:3306
│               (정적 파일)            (Flyway)      (볼륨)
└─────────────────────────────────────────────────────────────────
```

### 5-1. 시작 순서 보장  

```yaml
app:
  depends_on:
    mariadb: { condition: service_healthy }   # DB 준비 후 앱 시작
web:
  depends_on:
    app: { condition: service_healthy }       # Flyway 마이그레이션 끝난 뒤 nginx 시작 
```

- app의 healthy 판정은 app 이미지 Dockerfile의 `HEALTHCHECK`(`/actuator/health`) 사용
