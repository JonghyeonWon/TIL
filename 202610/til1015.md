## 1. Insecure DOR (접근 제어)  

- IDOR(Insecure Direct Object Reference): 로그인은 했지만 요청한 리소스가 본인 것인지 서버가 검사하지 않아, `{id}`만 바꾸면 남의 데이터에 접근되는 취약점  

### 1-1. 인증 vs 인가  

| 구분 | 질문 | 단계 |
| :--- | :--- | :--- |
| 인증 (Authentication) | 너 누구야? | 로그인으로 신원 확인 |
| 인가 (Authorization) | 이걸 볼/바꿀 권한이 있어? | 신원 확인 후 리소스 권한 확인 |

- IDOR은 인증은 통과했지만 인가가 빠진 경우에 속함 

### 1-2. DOR vs IDOR  

| 구분 | 뜻 | 취약 여부 |
| :--- | :--- | :--- |
| DOR | `/users/1`처럼 객체를 식별자로 직접 참조하는 것 | 정상 설계 |
| IDOR | 그 직접 참조에 권한 검사가 없는 경우 | 취약 |

### 1-3. 방어  

- 핵심은 객체 수준 인가: 요청자와 리소스 소유자를 대조해 본인 또는 관리자만 허용 → 아니면 403  

```java
if (!isAdmin && !isOwner) {
    throw new AccessDeniedException("본인 또는 관리자만 조회할 수 있습니다"); // 403
}
```

- 메서드에 `@PreAuthorize`를 붙이면 위와 동일한 검사를 한 줄로 처리 가능 (클래스용은 역할만 확인)

```java
@PreAuthorize("hasAnyAuthority('ROLE_USER','ROLE_ADMIN')")          // 클래스에 사용: 로그인한 USER/ADMIN만
@PreAuthorize("hasRole('ADMIN') or #id == principal.userInfo.id")   // 메서드에 사용: 관리자 또는 본인만
```

- 보조 방어 수단

| 방어 | 설명 |
| :--- | :--- |
| UUID 식별자 | id를 추측하기 어렵게 함 |
| 최소 노출 | 응답 DTO에 필요한 필드만 노출 (비밀번호 제외) |

## 2. Logging Hardening  

- 로깅·경보 실패(OWASP #9): 공격을 기록·감지·대응하지 못해 뚫렸는데도 모르는 상태가 되는 문제  

### 2-1. `SecurityAuditListener`  

```java
@Component @Slf4j
public class SecurityAuditListener {
    @EventListener
    public void onAuthenticationSuccess(AuthenticationSuccessEvent e) {
        log.info("[AUDIT] 로그인 성공 - user={}", mask(e.getAuthentication().getName()));
    }
    @EventListener
    public void onAuthenticationFailure(AbstractAuthenticationFailureEvent e) {
        log.warn("[AUDIT] 로그인 실패 - user={}, reason={}",
                 mask(e.getAuthentication().getName()),
                 e.getException().getClass().getSimpleName());
    }
}
```

| 이벤트 | 발행 시점 |
| :--- | :--- |
| `AuthenticationSuccessEvent` | 인증 성공 → `getAuthentication()`으로 사용자 정보 반환 |
| `AbstractAuthenticationFailureEvent` | 인증 실패 → `getException()`으로 실패 원인 반환 |

- `AbstractAuthenticationFailureEvent`는 실패 이벤트들(비밀번호 오류, 계정 잠김 등)의 부모 클래스 → 파라미터를 부모 타입으로 받아 메서드 하나로 모든 실패를 수신  

- 리스너를 직접 호출하는 코드는 없고 `AuthenticationManager`가 이벤트를 발행하면 Spring이 파라미터 타입이 일치하는 `@EventListener` 메서드를 찾아 자동 호출  

- 폼 로그인·REST 로그인 모두 `AuthenticationManager`를 거치므로 로그가 기록됨 

### 2-2. `DefaultExceptionAdvice`  

- 401·403 로그에 `[AUDIT]` 태그와 메서드·URI·IP를 남겨 누가 무엇을 시도했는지 파악  

```java
log.warn("[AUDIT] 접근 거부(403) - {} {} from {} : {}",
         request.getMethod(), request.getRequestURI(), clientIp(request), e.getMessage());
```

- 500 에러(OWASP #10 예외 처리 미흡 대응): 내부 로그엔 상세 + 트레이스, 외부 응답엔 일반 메시지 + traceId

```java
String traceId = newTraceId();
log.error("[ERROR][{}] {} {} : {}", traceId, request.getMethod(), request.getRequestURI(), e.getMessage(), e);  // 내부
errorObject.setMessage("서버 내부 오류가 발생했습니다. (traceId: " + traceId + ")");    // 외부
```

| 구분 | 내용 |
| :--- | :--- |
| 외부 응답 | `서버 내부 오류가 발생했습니다. (traceId: 9a51a868)` |
| 내부 로그 | `[ERROR][9a51a868] ... bad SQL grammar [SELECT ...]` |

- 같은 traceId로 사용자 문의와 내부 로그를 연결 가능 + SQL 구조 등 내부 정보는 노출 x

## 3. CSRF 

- CSRF(Cross-Site Request Forgery): 로그인된 사용자의 브라우저가 공격자 페이지에 의해, 본인도 모르게 상태 변경 요청(비밀번호 변경·이체 등)을 보내게 되는 공격  

- 브라우저는 요청할 때 해당 사이트의 쿠키(`JSESSIONID`)를 자동으로 첨부하기 때문에 취약  

```
[1] 피해자가 앱에 로그인 (JSESSIONID 보유)
[2] 피해자가 공격자 페이지 방문
[3] 공격자 페이지가 앱으로 위조 요청 전송 → 브라우저가 앱으로 가는 요청에 JSESSIONID를 자동 첨부
[4] 서버가 우리 화면에서 온 요청인지를 검증하지 않으면 위조 요청을 그대로 실행
```

### 3-1. 인증 방식별 CSRF 판단  

| 인증 방식 | CSRF 위험성 / csrf 옵션 활성화 필요 여부 | 이유 |
| :--- | :--- | :--- |
| 세션 + 쿠키 | 높음 → 반드시 활성화 | 쿠키가 자동 전송됨 |
| JWT (Authorization 헤더) | 낮음 → 비활성화 가능 | 헤더는 자동 전송되지 않음 |
| JWT (쿠키에 저장) | 높음 → 활성화 필요 | 다시 쿠키 자동 전송 대상이 됨 |

### 3-2. CSRF 토큰 동작  

- 서버가 세션마다 예측 불가능한 토큰을 발급해 폼에 심고, 요청 시 그 토큰이 함께 와야만 처리 → 공격자 페이지는 토큰 값을 알 수 없음  

- Thymeleaf `th:action` 폼에는 hidden `_csrf` 필드가 자동 삽입됨  

- `CsrfFilter` 처리 순서  

| 순서 | 동작 |
| :--- | :--- |
| 1 | GET/HEAD/TRACE/OPTIONS(안전한 메서드)는 검사 없이 통과 |
| 2 | POST/PUT/DELETE/PATCH는 세션에 저장된 기대 토큰을 꺼냄 |
| 3 | 요청의 `_csrf` 파라미터 또는 `X-CSRF-TOKEN` 헤더에서 토큰을 찾음 |
| 4 | 없거나 다르면 컨트롤러 도달 전에 403, 일치하면 통과 |

- 인증과 CSRF 검사는 별개의 필터 → 로그인한 뒤에도 상태 변경 요청마다 CSRF 토큰이 필요   

### 3-3. 상태 변경을 GET으로 받으면 안 되는 이유  

- CSRF 토큰은 GET에는 적용되지 않음(GET은 상태를 바꾸지 않는다고 전제하므로) → CSRF 옵션을 켜도 검사 없이 실행됨  

- 세션 쿠키(`JSESSIONID`)만 보내고 CSRF 토큰은 없이 요청한 경우  

| 요청 | CSRF 비활성 | CSRF 활성 |
| :--- | :--- | :--- |
| `GET /users/delete/{id}` | 삭제됨 | 삭제됨 (GET은 검사 대상 x) |
| `POST /users/delete/{id}` | 삭제됨 | 403 → 차단 |

- 방어는 CSRF 토큰 + "상태 변경은 GET으로 실행 X" 두 가지가 동시에 필요

## 4. JWT (JSON Web Token)  

- `header, payload, signature`를 각각 `.`으로 이은 문자열 (각각 base64url 인코딩)  

| 부분 | 내용 |
| :--- | :--- |
| header | 알고리즘 (`{"alg":"HS256"}`) |
| payload | 클레임 (`sub`, `iat`, `exp` 등) |
| signature | header + payload를 secret으로 서명한 값 |

### 4-1. 핵심 개념  

- 서명 ≠ 암호화: payload는 base64 인코딩의 결과 → 누구나 디코딩 가능 → PII(email 등 개인 식별 정보)를 넣지 않아야 안전  

- 서버는 우리 secret으로 서명됐는가만 확인 

- HS256은 발급·검증에 같은 secret을 쓰므로 secret이 유출되면 누구나 토큰을 위조 가능 

### 4-2. Secret 관리  

- 소스 코드나 `application.properties`에 실제 secret을 두면 취약 → 환경변수 / 시크릿 매니저(Vault 등)에 보관

```properties
jwt.secret=${JWT_SECRET}
# true(약한 secret 허용), false(약한 secret이면 기동 거부)
jwt.allow-insecure-secret=${JWT_ALLOW_INSECURE_SECRET:true}
```

```java
boolean weak = secret == null || secret.isBlank()
    || secret.getBytes(StandardCharsets.UTF_8).length < 32   // HS256 최소 길이
    || KNOWN_WEAK_SECRETS.contains(secret.trim());           // 알려져 취약해진 시크릿 값

if (weak && !allowInsecureSecret) throw new IllegalStateException("약한/기본 secret");
```

- `allow-insecure-secret=false`일 때 secret이 약하면(32byte 미만, 알려진 값) 앱이 아예 기동하지 않음

- `KNOWN_WEAK_SECRETS`는 미리 등록한 값만 거부 → 새로 만든 secret이 나중에 유출돼도 코드는 감지하지 못함

- 유출을 알면 즉시 교체, 모르는 유출에 대비해 정기적으로 로테이션
