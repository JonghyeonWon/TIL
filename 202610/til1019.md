## 1. 보안 설정 오류 (Security Misconfiguration)  

- 코드의 로직 결함이 아닌 설정에서 기본 보호 기능을 꺼버려서 생기는 취약점 

- 대표 예시: 기본 비밀번호 사용, 불필요한 기능 활성화, 상세 오류 노출 등

### 1-1. Spring Boot Actuator  

- 운영 모니터링을 위해 애플리케이션 내부 상태·설정을 보여주는 엔드포인트 제공  

| 엔드포인트 | 보여주는 것 |
| :--- | :--- |
| `/actuator/health` | 서버 생존 여부 |
| `/actuator/info` | 앱 정보 |
| `/actuator/metrics` | 측정된 지표 값 |
| `/actuator/env` | 현재 적용된 설정값 |
| `/actuator/beans` | 스프링 빈 목록 |
| `/actuator/mappings` | 모든 URL 매핑 |

- 운영 점검엔 유용한 기능이지만, 인증 없이 누구나 조회 가능하면 그 자체로 취약  

### 1-2. 취약한 설정  

```properties
management.endpoints.web.exposure.include=*      # 모든 엔드포인트 노출
management.endpoint.env.show-values=always       # 값 마스킹 기능을 끔
```

| 설정 | 문제 |
| :--- | :--- |
| `exposure.include=*` | env·beans·mappings까지 전부 외부에서 조회 가능 |
| `show-values=always` | secret 등의 민감 정보들이 평문으로 노출됨 |

- `show-values`는 반드시 `never`(기본값) 유지 필요

- 한 번이라도 노출된 비밀키는 재사용하지 말고 교체(rotate)  

### 1-3. 방어  

- 꼭 필요한 엔드포인트만 열어서 노출 범위를 최소화  

```properties
# health,info,metrics만 노출
management.endpoints.web.exposure.include=${ACTUATOR_EXPOSURE:health,info,metrics}
```

- 심층 방어: `SecurityConfig`에서 추가로 관리자 권한을 요구  

```java
// SecurityConfig.formLoginFilterChain()
.requestMatchers("/actuator/health", "/actuator/info").permitAll()   // 외부 모니터링용 -> health, info는 노출
.requestMatchers("/actuator/**").hasAuthority("ROLE_ADMIN")          // 나머지는 관리자만 허용
.anyRequest().permitAll();
```

### 1-4. Micrometer  

- 애플리케이션 지표(metric)를 측정하기 위한 벤더 중립 계측 라이브러리  

- 로깅의 SLF4J와 비슷한 위치 → 코드는 공통 API만 호출하고, 지표를 어디로 보낼지는 구현체가 결정  

- `MeterRegistry`: 앱 안의 모든 카운터를 이름표 붙여 모아두는 집계판  

   - Spring Boot가 빈으로 자동 생성 → 생성자 주입만 받으면 바로 사용 가능

   - 사건이 몇 번 일어났는지 숫자를 누적  

```
[1] 로그인 성공 이벤트 발생 (SecurityAuditListener)
[2] meterRegistry.counter("auth.events", "result", "success") → 집계판에서 해당 카운터를 찾음 (없으면 새로 만듦)
[3] .increment() → 그 카운터 값 +1
[4] 관리자가 /actuator/metrics/auth.events 조회 → 집계판에 쌓인 값을 응답
```

```java
//                      지표 이름      태그 키     태그 값
meterRegistry.counter("auth.events", "result", "success").increment();   // 로그인 성공 +1
meterRegistry.counter("auth.events", "result", "failure").increment();   // 로그인 실패 +1
```

- `counter()`는 같은 이름+태그면 항상 같은 카운터를 돌려줌 → 호출할 때마다 새로 생기는 게 아니라 같은 숫자에 계속 누적됨  

- 태그(tag): 지표 이름(`auth.events`) 아래 `result=success/failure`로 차원만 나눔 → 성공용·실패용 지표를 따로 만들지 않고 한 지표를 여러 각도로 조회  

- `admin/monitoring.html`에서 태그로 필터링해 확인  

```html
<a th:href="@{/actuator/metrics/auth.events(tag='result:success')}" target="_blank">
    /actuator/metrics/auth.events?tag=result:success</a>   <!-- 성공 건수만 -->
```

- 새 조회 경로도 `/actuator/**` → `ROLE_ADMIN` 규칙을 그대로 적용받음 → 기능을 넓혀도 보호는 유지 가능

## 2. 역직렬화 무결성 실패 (Insecure Deserialization)  

- 무결성 실패: 데이터나 코드가 검증 없이 바뀔 수 있는 문제  

- 클라이언트가 보낸 값을 역직렬화했을 때 그 값은 항상 위조될 수 있다는 점을 고려해야 함  

| 용어 | 뜻 |
| :--- | :--- |
| 직렬화 | 객체 → 바이트/문자열 |
| 역직렬화 | 바이트/문자열 → 객체 |

```
직렬화 과정: 객체 → byte[] (ByteArrayOutputStream, ObjectOutputStream) → Base64 인코딩

역직렬화 과정: Base64 디코딩 → byte[] (ByteArrayInputStream, ObjectInputStream) → 객체
```

| 클래스 | 역할 |
| :--- | :--- |
| `ByteArrayOutputStream` + `ObjectOutputStream` | 객체를 바이트로 변환해 메모리에 쌓음 (직렬화) |
| `ByteArrayInputStream` + `ObjectInputStream` | 바이트를 다시 객체로 복원 (역직렬화) |

### 실습 예시: 할인 쿠폰(Voucher)  

- 이하 2번의 모든 예시는 할인 쿠폰 기능을 기준으로 함  

```java
public class Voucher implements Serializable {
    private String code;             // 쿠폰 코드 (예: WELCOME10)
    private int discountPercent;     // 할인율 (예: 10)
    private String issuedToUuid;     // 발급 대상
}
```

| 단계 | 흐름 |
| :--- | :--- |
| 발급 | 서버가 쿠폰 코드로 할인율을 정해 `Voucher` 생성 → 직렬화 + Base64 한 `voucherToken`을 클라이언트에 전달 |
| 보관 | 클라이언트가 토큰을 들고 있음 → 이 동안 열어보고 고칠 수 있음 |
| 제출 | 결제 시 토큰을 서버로 돌려줌 → 서버가 역직렬화해 할인 적용 |

### 2-1. 취약점 원리  

- `int` 필드(discountPercent)는 직렬화 스트림에 고정 4바이트(빅엔디안)로 그대로 들어감 → 4칸만 덮어쓰면 값이 바뀜  

```
할인율 10  : 00 00 00 0a
할인율 100 : 00 00 00 64
```

- 역직렬화 성공 ≠ 변조되지 않음 (포장이 멀쩡하다고 내용물을 믿어도 되는 것은 아님)  

### 2-2. 방어 - 재검증  

- 토큰 안의 할인율이 아니라 `code`를 꺼내 서버에서 다시 조회  

```java
// COUPON_POLICY: 서버가 가진 쿠폰 코드별 할인율 맵 (예: WELCOME10 → 10)
int trustedDiscountPercent = COUPON_POLICY.getOrDefault(voucher.getCode(), 0);
```

- 클라이언트가 보낸 할인율 값은 결과 계산에 쓰지 않음 → `code`는 어떤 값을 찾을지 알아내는 단서로만 사용  

### 2-3. 방어 - HMAC 서명  

- HMAC(Hash-based Message Authentication Code): 데이터가 바뀌지 않았다는 것을 증명하는 지문  

- 일반 해시와 다르게 서버만 아는 비밀키를 섞음

- 비밀키가 없는 공격자는 내용을 바꾼 뒤 맞는 서명을 새로 만들 수 없음  

- 토큰 형태: `base64(직렬화 바이트) + "." + base64(HMAC 서명)` 

### 2-4. 서명에 쓰이는 클래스  

| 클래스 | 역할 |
| :--- | :--- |
| `javax.crypto.spec.SecretKeySpec` | 원시 바이트 배열 + 알고리즘 이름을 받아 암호 API가 이해하는 `SecretKey` 규격 객체로 래핑 |
| `javax.crypto.Mac` | 비밀키와 데이터로 MAC(인증 코드)을 계산 → 무결성 + 송신자 인증 보장 (`HmacSHA256`, `HmacSHA512` 등) |
| `java.security.MessageDigest` | 데이터 위·변조 확인, 여기선 `isEqual()`로 두 서명을 상수 시간 비교 (`==`처럼 중간에 멈추지 않아 타이밍 공격 방지) |

- 상수 시간 비교: 어디서 달라지든 비교에 걸리는 시간이 항상 같음  

| 비교 방법 | 동작 | 결과 |
| :--- | :--- | :--- |
| `==`, `Arrays.equals` | 다른 바이트를 만나면 즉시 멈춤 | 응답 시간 차이로 앞 몇 바이트가 맞았는지 새어 나감 → 한 칸씩 맞춰 서명 추측 가능 |
| `MessageDigest.isEqual` | 항상 끝까지 비교 | 시간이 같아 얻을 정보 없음 |

- 흐름: `SecretKeySpec`으로 비밀키 준비 → `Mac`에 주입(`init`) → 데이터의 서명 생성  

```java
SecretKeySpec hmacKey = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"); // 키 준비
Mac mac = Mac.getInstance("HmacSHA256");   // 알고리즘 지정
mac.init(hmacKey);                         // 키 주입
byte[] signature = mac.doFinal(data);      // 서명 생성
```

### 2-5. 서명 검증  

- 서버는 서명을 해독하지 않고, 받은 내용으로 서명을 다시 만들어 받은 서명과 같은지만 비교  

```java
byte[] expected = hmac(raw);    // 받은 내용으로 다시 계산

if (!MessageDigest.isEqual(expected, signature)) {  // 서명이 같은지 상수 시간 비교
    throw new IllegalArgumentException("서명이 유효하지 않습니다");
}
return deserializeFromBytes(raw);   // 통과해야만 역직렬화
```
